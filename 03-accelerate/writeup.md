# 03-accelerate：核场响应加速

## 1. 题目要计算什么

对每个查询点 `points[q]`，程序都要遍历全部参数组 `c`。每组参数先做两次长度为 `D` 的循环：一次算到中心的平方距离，一次算方向向量点积；随后分别调用指数和正弦函数，并把两项加到该查询点的结果中。最后返回 `Q` 个 `float32` 数。

以公开大样例为例，`Q=98,304`、`C=10,240`、`D=32`。这意味着大约 10 亿个“查询点-参数组”组合，每个组合又要处理 32 个维度。原始 Python 实现有三层 Python 循环，还在最内层反复把 NumPy 数值转成 Python `float`，解释器开销会非常大。

## 2. 当前实现怎么工作

### 第一步：把大量循环放到 C 内核中执行

把逐点、逐参数组、逐维度的循环写成 `solver.py` 内嵌的 C 源码。每个参数组仍然完整计算距离、点积、高斯项和正弦项，没有使用样例答案、近似跳过参数组，也没有缓存上一次调用的结果。C 源码由 `solver.py` 在导入时交给 GCC 临时编译；生成的共享库放在系统临时目录，不作为提交文件携带。

这样做的原因是：C 编译器能直接处理连续的 `float32` 数组和紧凑循环，不必为几十亿次迭代创建 Python 对象或执行 Python 层循环。距离、点积、跨参数组累加仍由本题自己的内核完成，没有交给 NumPy/BLAS 等外部计算库。

### 第二步：按查询点并行

不同查询点互不依赖：计算 `out[q]` 时只读取输入，并只写 `out[q]`。因此内核使用 OpenMP 把外层查询点循环分给多个 CPU 线程。一个查询点内部的参数组仍按原顺序累加，线程之间没有共享的求和变量，也不需要锁或跨线程归约。

评测环境会设置 `OMP_NUM_THREADS`。小输入少于 16 个查询点时不启动并行循环，避免线程管理成本超过计算本身。

### 第三步：使用单精度中间值，保留双精度总和

输入和返回数组为 `float32`。当前内核用 `float` 计算平方距离和点积，并调用 `expf`、`sinf`；每个查询点的总和用 `double` 累加，最后转换成 `float32`。每组参数仍完整计算两项贡献，再继续累加。这里描述的是当前源码的实现方式，不代表本轮测量重新比较或证明了“从双精度改成单精度”的提速幅度。

单精度中间值会产生舍入误差，不能只凭输入类型推断正确。下面的公开大样例检查使用题目公开自测脚本所用的比较条件 `abs(a-b) <= 1e-5 + 1e-4*abs(b)`；正式隐藏正确性用例仍以 OJ 结果为准。

### 第四步：在提交环境编译内核

GCC 首先尝试 `-Ofast -march=native`，如果该编译命令失败，就回退到 `-Ofast`。内核共享库由源码在模块准备阶段临时构建，不随提交包携带。题目不计入环境准备与导入时间；每次正式 `compute_field` 调用仍会同步完成全部输入相关计算并返回结果。

`-Ofast` 允许更积极的浮点变换，因此每次改编译选项后都要重新检查正确性。当前代码不依赖具体样例，不读取参考文件，也不跨调用缓存输入相关结果。

## 3. 如何复现与验证

工作区代码和公开数据放在本机仓库。小样例曾在私人服务器 `legion` 上运行；该机有 24 个 x86 物理核，适合检查程序与公开参考答案，不适合作为官方 32 核 ARM 性能的代理。为检查 32 核 CPU 路径，另通过官方说明中的 `kp_run` 队列申请单节点 32 核 `sbatch` 作业；所有编译和基准均在计算节点内执行。

```bash
rsync -az -e ssh 03-accelerate/ legion:~/hellohpc-contest/03-accelerate/
ssh legion 'cd ~/hellohpc-contest/03-accelerate && python3 benchmark.py sample --cpu-list 0'
```

`sample` 检查函数接口、输出类型和公开参考答案。当前 `legion` 有 24 个物理核，而题目公开性能估分脚本要求 32 个物理核，所以它不能产生与比赛同口径的正式性能分。large-b 的受限环境复核使用 24 核，步骤是：加载 `public-large-b.npz`，先用最多 2,048 个查询点和 48 组参数预热；再完整调用三次 `compute_field`；每次将结果与 `public-large-b.ref.txt` 按 `atol=1e-5, rtol=1e-4` 比较，并记录三次调用耗时的最大值。正式评测使用 32 核，结果应以 OJ 为准。

legion 上曾有单精度候选的误差与耗时记录，但本轮没有重新复跑，且 legion 与官方 ARM 计分环境不同，故不把旧记录作为当前性能结论。当前源码在交我算 CPU 队列上的公开大样例结果如下。测试由仓库 `benchmark.py` 独立脚本运行，固定每个全新 worker 预热一次、测三次并取最大值；它与默认公开配置相同，采用相同的 `timing.py` 同步调用计时协议，但不是 `hellohpc test` 的正式编排，因此下列都是本地公开数据代理测量，不是 OJ 评分：
