# 03-accelerate：核场响应加速

## 1. 题目要计算什么

对每个查询点 `points[q]`，程序都要遍历全部参数组 `c`。每组参数先做两次长度为 `D` 的循环：一次算到中心的平方距离，一次算方向向量点积；随后分别调用指数和正弦函数，并把两项加到该查询点的结果中。最后返回 `Q` 个 `float32` 数。

以公开大样例为例，`Q=98,304`、`C=10,240`、`D=32`。这意味着大约 10 亿个“查询点-参数组”组合，每个组合又要处理 32 个维度。原始 Python 实现有三层 Python 循环，还在最内层反复把 NumPy 数值转成 Python `float`，解释器开销会非常大。

## 2. 优化步骤

### 步骤一：保留全部计算，只改变循环执行位置

把逐点、逐参数组、逐维度的循环写成 `solver.py` 内嵌的 C 源码。每个参数组仍然完整计算距离、点积、高斯项和正弦项，没有使用样例答案、近似跳过参数组，也没有缓存上一次调用的结果。C 源码由 `solver.py` 在导入时交给 GCC 临时编译；生成的共享库放在系统临时目录，不作为提交文件携带。

这样做的原因是：C 编译器能直接处理连续的 `float32` 数组和紧凑循环，不必为几十亿次迭代创建 Python 对象或执行 Python 层循环。距离、点积、跨参数组累加仍由本题自己的内核完成，没有交给 NumPy/BLAS 等外部计算库。

### 步骤二：按查询点并行

不同查询点互不依赖：计算 `out[q]` 时只读取输入，并只写 `out[q]`。因此内核使用 OpenMP 把外层查询点循环分给多个 CPU 线程。一个查询点内部的参数组仍按原顺序累加，线程之间没有共享的求和变量，也不需要锁或跨线程归约。

评测环境会设置 `OMP_NUM_THREADS`。小输入少于 16 个查询点时不启动并行循环，避免线程管理成本超过计算本身。

### 步骤三：在误差范围内降低中间运算成本

输入和返回数组为 `float32`。最初版本使用双精度计算距离、点积，并调用双精度 `exp` 和 `sin`；在大样例上这部分成本明显。新候选版本让距离、点积及 `expf`、`sinf` 使用单精度，查询点的总和仍以 `double` 累加，最后转换为 `float32`。每组依然先加高斯项，再加正弦项，没有跳过任何参数组。

单精度中间值会产生舍入误差，因此不能仅凭“float32 输入”就假定正确。我在 `legion` 上对完整公开大样例逐元素套用正式误差式 `abs(a-b) <= 1e-5 + 1e-4*abs(b)` 检查，最大绝对误差约 `9.54e-6`，最大误差/容差比约 `0.536`，全部通过；`sample` 也通过参考答案检查。正式隐藏正确性用例仍需以 OJ 验证为准。

### 步骤四：只在支持时启用本机指令优化

GCC 首先尝试 `-Ofast -march=native`，让编译器针对运行机器选择指令并优化循环。如果编译器不支持 `-march=native`，就回退到 `-Ofast`。代码没有生成或提交预编译内核；每个干净进程都会从 `solver.py` 中的源代码构建临时共享库。

`-Ofast` 允许编译器进行更积极的浮点变换，因此不能仅凭理论推断它一定符合容差；每次修改编译选项后都需要重新跑正确性检查。本次公开测试在启用该选项后与参考输出逐元素相同。

## 3. 如何复现与验证

工作区代码和公开数据放在本机仓库；根据赛前约定，运行测试只在私人服务器 `legion` 上执行：

```bash
rsync -az -e ssh 03-accelerate/ legion:~/hellohpc-contest/03-accelerate/
ssh legion 'cd ~/hellohpc-contest/03-accelerate && python3 benchmark.py sample --cpu-list 0'
```

`sample` 检查函数接口、输出类型和公开参考答案。当前 `legion` 有 24 个物理核，而题目公开性能估分脚本要求 32 个物理核，所以它不能产生与比赛同口径的正式性能分。large-b 的受限环境复核使用 24 核，步骤是：加载 `public-large-b.npz`，先用最多 2,048 个查询点和 48 组参数预热；再完整调用三次 `compute_field`；每次将结果与 `public-large-b.ref.txt` 按 `atol=1e-5, rtol=1e-4` 比较，并记录三次调用耗时的最大值。正式评测使用 32 核，结果应以 OJ 为准。

本次验证记录：

| 测试 | 结果 |
|---|---|
| `sample`，legion 单核 | 通过；约 1.0–2.3 ms |
| `public-large-b`，legion 24 核，原双精度中间值 | 三次均通过；约 1.51、1.54、1.62 秒；最大绝对误差为 0 |
| `public-large-b`，legion 24 核，单精度中间值候选 | 三次均通过；约 0.89、0.91、0.98 秒；最大绝对误差约 `9.54e-6` |

在用户指定的交我算 CPU 集群上，我先现查到 `kp_run` 可用，并通过 `sbatch` 申请 32 核单节点运行。集群默认 Python 3.9 没有 NumPy；我在作业分配的计算节点内建了隔离虚拟环境并安装 NumPy，没有在登录节点编译或运行基准。三组公开大样例对照结果如下：

| 版本 | 节点 | 三次耗时（ms） | 最大值 | 正确性 |
|---|---|---:|---:|---|
| 当前版本 | kp032 | 2078.100, 1822.511, 1834.872 | 2078.100 | 通过 |
| GCC 展开 32 维内循环 | kp040 | 2167.656, 1883.015, 1816.244 | 2167.656 | 通过 |
| 去掉 `omp simd reduction` 提示 | kp042 | 1808.445, 1800.599, 1797.364 | 1808.445 | 通过 |
| 同节点复测：当前版本 | kp042 | 1893.518, 1867.148, 1783.302 | 1893.518 | 通过 |
| 同节点复测：无 SIMD 提示 | kp042 | 1901.049, 1842.431, 1845.831 | 1901.049 | 通过 |
| 最终当前版本复测 | kp032 | 1815.535, 1834.191, 1808.553 | 1834.191 | 通过 |

同节点对照显示，去掉 SIMD 提示没有稳定加速（最大值反而略慢），所以保留原来的 `omp simd reduction`。按题目对三次取最大值的规则，表中六组测试的本地代理分数依次约为 41.86、41.23、43.92、43.24、43.18、43.71/50。不同节点结果可能受频率和系统负载影响，不能据此断言跨节点的细小差异来自代码。legion 上的 24 核 x86 结果也不能与交我算 32 核 ARM 节点横向比较。

工作区中的 [最新测评结果.md](最新测评结果.md) 记录了最近一次 OJ 回报：四个正确性项各 5 分；`large-a` 为 843.433806 ms、25.06/30；`large-b` 为 1891.555843 ms、43.25/50。按该文件列出的各项分数相加，总分为 **88.31/100**。这覆盖了当前提交的表现；隐藏的四个正确性用例仍应以 OJ 的 accepted 状态为准。

优化实验也验证了为什么需要实测：平方距离改写成 `||x||² + ||mu||² - 2*x·mu` 在 legion 上正确但没有提速；转置中心/方向数组后反而约慢三倍；GCC 展开维度循环在官方队列节点上也更慢。它们均不保留在提交代码中。当前可确认的结论是：现有 C/OpenMP 内核正确、性能已有有效分数，而这几项低风险循环变换没有可靠收益。下一步若继续优化，应针对 `expf`/`sinf` 的向量化和目标编译器生成代码做有针对性的验证，并逐次运行完整公开参考检查。
