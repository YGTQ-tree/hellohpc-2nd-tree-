# Rune 题解记录

## 1. 先弄清题目要做什么

Rune 是一个集群调度模拟题。模拟器会不断告诉策略当前有哪些任务已就绪、哪些任务正在运行、每个 Worker 是否可用以及它目前占用了多少 CPU 和内存。策略要为就绪任务挑选 Worker，目标是让最后一个任务尽可能早地完成。

策略只能使用两类信息：固定公开的 `PublicScenarioModel`，以及当前时刻的 `Observation`。Seed 决定但尚未发生的任务释放、派生任务、失败和停机结果不可见。因此实现不读取 Seed、不根据 Profile 名称选择方案，也不使用历史运行结果作为运行时输入。

本题会严格检查资源合法性。Worker 必须可用、必须具有任务所需的所有能力；同一 Worker 上已预留与新预留的内存不能超过容量。CPU 超量本身不使场景无效，但会让任务变慢。没有当前可放置任务时，必须返回 `DEFER` 和空 placements，让模拟时间推进到下一个事件。

## 2. 从安全的最小策略开始

第一步是在构造函数中把任务类型和 Worker 规格按 ID 建成字典。这样每次决策都能直接查到任务的内存、CPU、能力要求，以及 Worker 的容量和执行速度。速度倍率 `ratio = 1/4` 表示完成同样工作只需四分之一时间；未为某个任务类型列出倍率时，按默认倍率 1 估算。

每个决策点先查看 `ready_tasks`。对每项任务逐个过滤 Worker：只留下当前 `available`、能力集合满足要求、剩余内存足以容纳该任务的 Worker。选中一个任务后，立刻在本地预算中扣除它的内存和 CPU；因此同一次提交中的后续任务不会重复使用已经分配的资源。单批 Placement 数量也限制在公开的 `max_batch_size` 以内。

如果筛完没有任务能安全放置，返回 `DispatchAction.DEFER`。绝不返回空的 `DISPATCH`，也不把不可用 Worker、能力不足或内存不足的分配交给评测器处理。

## 3. 让在线决策照顾后续工作

只按当前任务运行时间排序会让短任务挤走关键链路上的任务。实现会从公开的两种依赖关系中建立任务类型的后继图：完成后会派生任务的 `Derivation`，以及工作流节点之间的 `depends_on`。从当前类型向后估计一条可能的最长工作链，作为任务关键性分数。后续还有较多工作要做的任务通常更早安排。

这是通用优先级，不依赖任何隐藏任务数量。派生关系只表示“可能出现的后继类型”，并不假定它们未来何时出现或出现多少。为避免图中意外循环造成递归问题，计算时记录当前访问路径并在遇到循环时停止该分支。

有些任务只能交给少数具备专用能力的 Worker。策略统计当前每项就绪任务有多少个可行 Worker，并优先保护可选 Worker 较少的任务，避免通用任务先占用稀缺资源。失败次数较多的任务在其它因素相同时略微靠前，以免重试工作一直被推迟。

## 4. 估算 Worker 负载与 setup

为挑 Worker，策略估算每个 Worker 当前还有多少工作。运行阶段用任务类型平均运行工作量减去已完成的运行服务量；setup 阶段不把 setup 服务量误当成任务运行进度。CPU 使用比例会影响估算速度，公开的 Worker 速度倍率也会参与估算。

相同 Worker、同一决策点、同一任务类型的多个新任务会共享一次 setup。策略在逐项构造批次时记录这种组合：同组第一个任务承担 setup 估算成本，后续任务不重复计算。对已运行中的 setup 组，也按共享组估算安装工作，而不是把同一份 setup 错算成每个任务都要独立完成。

策略会把预计新增负载和预计完成跨度合成 Worker 选择分数。对存在 outage 先验的 Worker 增加有限的风险惩罚，避免在速度近似时过分偏向更容易停机的 Worker。outage 只是先验估计，策略不尝试推断随机停机的确切未来时刻。

## 5. 控制并发，并在慢 Worker 前等待

最初的试验显示，只要有内存空间就持续提交任务，容易使 Worker 的 CPU 需求远超容量；超额虽然合法，却会让 Worker 上所有任务按比例变慢。因此当前批次会优先把 CPU 总需求控制在容量以内。若一个 Worker 原本没有负载，单个任务自身需求高于容量仍可放置，因为它不会造成同批任务彼此争抢，而且题目只把 CPU 超量作为性能影响。

把任务分给任意可用 Worker 也不一定划算：一个很慢的 Worker 可能长期占住新任务，而稍后当前忙碌的快 Worker 就会空出来。策略用当前观测到的负载，比较“现在交给可用 Worker”与“等当前兼容 Worker 完成手头工作后的估计完成时间”。如果可用 Worker 明显慢于当前最佳估计，且系统确有活动工作或当前批次已经有提交，就先不把该任务放到慢 Worker；若本轮没有其它任务可派，策略返回 `DEFER`。

这个等待规则只使用现有 active attempts、Worker 规格与当前就绪任务，不假设未来释放时间，也不查看后续 Seed 事件。它是估算启发式，可能在少数情况下等待过久，所以最终仍需用多个种子测量。

## 6. 测试方法与当前结果

按照本次约定，测试都在私人服务器 `legion` 上完成，没有在这台电脑执行模拟。远端是 x86_64，所以选择题目提供的 `rune-cluster-x86`。系统自带 Python 3.12，不满足题面 Python 3.13 要求；我用远端 Miniforge 单独创建了 `rune-313` 环境，没有改动其它环境。

单场景运行形式如下，Seed key 使用题目公开默认值：

```bash
HELLOHPC_OUTPUT=/tmp/rune-result.json \
python run_scenario.py \
  --policy policy.py \
  --profile profiles/profile-01.toml \
  --seed-count 1 \
  --zero-time 1490 \
  --seed-key 000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
```

先用 profile-01 的单个 Seed 验证程序能启动、策略能与模拟器交互，结果为有效，Makespan 为 1378。随后用 2 个种子跑全部 18 个 Profile，检查每个场景的 `scenario_valid`。优化过程中对比了多个通用启发式版本，最终采用了限制 CPU 并发和必要时等待更合适 Worker 的方案。接着最新版对全部 Profile 各运行 8 个 Seed；截至记录时，profile-01 到 profile-17 均为有效场景，均值分别为：

## 7. 提交前检查

正式提交只包含 `policy.py`。模拟器、Profile、二进制文件与执行器均为只读评测资产，不修改、不探测隐藏信息，也不在策略中硬编码 Profile 或 Seed 特例。`writeup.md` 是学习记录，不属于提交文件。

本地检查使用 `git diff --check` 确认没有空白错误，并在远端用 Python 3.13 运行 `py_compile`。当前已完成 profile-01 单 Seed 验证、全 Profile 2 Seed 验证，以及全 Profile 8 Seed 测试；所有测试场景均报告 `scenario_valid = 1`。正式评测使用 64 个 Seed，并会扰动 Profile 数据和 Seed key，因此不能把 8 Seed 结果视为成绩保证。
