# 竞赛作答总指南（主入口 · 给后续 Agent）

> **这份文档的定位**：接手 **HelloHPC 2nd（2026）真正比赛题**时的第一读物。
> 它把 2024 XFLOPS 校内赛 + 2025 HelloHPC 1st 两次比赛、共 15 道题的实战经验，压缩成一份可执行手册。
>
> **前两年的题现在都无法提交**（数据下线、OJ 关闭），仓库里的实现只是**参考答案/经验素材**；
> 本文档的作用是让后续 agent **不必重新踩坑**，直接对今年的新题面干活。
> 规则红线的全文在 `05`，集群环境的最新事实与实测依据在 `04`，技巧卡全集在 `02`，知识栈在 `01`，可执行条款在 `03`。

## 0. 30 秒版：拿到一道新题后的标准动作

```
1. 读 readme.md   → 钉死【评分标准】和【提交文件】
2. 读 submit.yaml → 只允许交哪些文件（决定你能改什么）
3. 读 evaluate.py → 怎么编译、怎么跑、计时段在哪、分数怎么算、输出怎么被解析
4. 跑 download.sh 前先确认数据还在（/lustre/share/xflops 整棵树已不存在，见 §3.4）
5. 用【官方原始代码】跑一次 baseline，记录时间与数值（后面所有对比的锚点）
6. 判断计分类型（§3.3 达标型 vs 相对最优型）→ 决定"要做到多快就够"
7. 定位热点 → 优化 → 对拍正确性 → 集群实测（≥3 次取中位数）→ 写 writeup → 打包提交
```

**贯穿全程的两条铁律**：
- **绝不伪造结果**（不硬编码答案、不打表、不改判题输出、不把计算挪出计时段）；
- **每次优化后都要对拍**，证明"结果没变"，而不是"我觉得没变"。

## 1. 硬性规则与红线（摘要）

> 完整解读、✅/❌ 代码示例、违规后果、自查清单：**`05_比赛规则与红线.md`**。这里只放判定用的最短版本。

| # | 规则 | 具体要求 |
|---|------|---------|
| 1 | 诚信 | 个人赛；不许抄袭、不许交流答案、不许伪造数据（会查重） |
| 2 | 不许攻击评测 | 不许打评测机、探测/攻击判题服务、DoS |
| 3 | **不许打表** | 不许把样例答案写进代码、不许按输入特判、不许依赖特定数据分布、不许读 `ref*` 反推 |
| 4 | **计算不得挪出计时段** | 不许用异步线程/后台线程/全局构造/跨调用缓存，把计时段内的计算提前、延后或挪走 |
| 5 | AI 使用 | 允许，但**必须理解提交的每一行**；并遵守 OJ「Agent 辅助答题」条款（正文待确认，见 05 §6） |
| 6 | 登录节点纪律 | 不许在登录节点跑重活（并行编译、benchmark、多线程程序）→ 一律走 sbatch |
| 7 | 账号 | 只用于本次比赛，不转借、不跑无关作业、不浪费资源 |
| 8 | 代码审查 | 提交**可读的原始源码**；不许混淆、不许交编译产物；`writeup.md` 是计分项 |

**每题提交前的 4 连问**

1. 我把计时区内的代码换成 `sleep`，结果还对吗？→ 对，说明我把计算挪出去了（违反规则 4）
2. 我的答案是不是只对这一个输入成立？→ 是则违反规则 3
3. `submit.yaml` 列的文件我是不是都产出了、没多交没少交？
4. 我能不能不看笔记，把这道题的优化原理讲 5 分钟？

> 规则 4 最常见的踩法：把"初始化/预计算"挪到全局对象构造里，或在第一次调用时缓存结果供后续调用复用。
> 计时区间由本题 `evaluate.py` / `main` 决定，**只优化计时区间内的代码**。

### 2.2 ★ 第一步永远是重新探测分区

队列名每年都会变（旧文档里的 `kp920race` / `kp920vscode` 已经消失，`kp_run` 之类也可能变）——**用命令问，不要猜**：

```bash
ssh arm 'bash -lc "scontrol show partition | grep PartitionName"'      # 全量（别用 sinfo | head，会截断）
ssh arm 'bash -lc "sinfo -o \"%20P %6D %5c %8m %12l %6t\""'
ssh arm 'bash -lc "sacctmgr -n show assoc user=\$USER format=Account,QOS%40"'
ssh arm 'bash -lc "sacctmgr -n show qos format=Name,MaxTRESPerUser%30,MaxJobsPerUser"'
```

2026-09-21 实测（**仅作对照**）：`kp_run` 有 23 个 idle 节点（128 核 / 2h，**128 核题的主力**）；
`kp_interact`（节点 128 核但 **QOS 只给 8 CPU** / 8h）；`64c512g`(x86 64 核)、`cpu`(40 核)、`192c6t`、`huge`、`small`、`el9`、`win32`、
`a100`/`a800`/`dgx2`(GPU)、`scnet_arm`；`arm128c256g` 与 `debugarm` **常年 drain/down**；`kp_judge` 是评测专用，别碰。

### 2.3 sbatch 模板与填写规范

```bash
#!/bin/bash
#SBATCH -J <name>
#SBATCH -p kp_run          # 分区（现探）
#SBATCH -q kp_run          # QOS，名字常与分区同名；不写报 Invalid qos specification
#SBATCH -A acct-stu        # 账户，必须写
#SBATCH -N 1
#SBATCH -c 128             # ★ 不要写 --mem
#SBATCH -t 01:00:00
#SBATCH -o ~/<work>/slurm_%j.out
cd "$SLURM_SUBMIT_DIR"     # 一定要 cd：sbatch 的工作目录是提交时的 cwd
echo "HOST=$(hostname) nproc=$(nproc)"    # 先确认拿到了几核
<你的命令>
```

- **不要写 `--mem`**：默认 **1950 MB/核**（`-c 128` ⇒ 约 244 GB）。写大了会被**折算成更多 CPU** → 撞 QOS 上限。
- **内存不够会被 OOM kill，而且常常不打印程序最后一行** → 判题解析不到 → 0 分。宁可多要核（核多内存就多）。
- **QOS 常限制 `MaxJobs=1, MaxSubmitJobs=1`** → 重提前先 `scancel -u $USER` + `squeue -u $USER` 确认空。
- **`srun` 起不了 OpenMPI**（`MPI_Init` 拿不到 communicator）→ MPI 用 `sbatch` + `mpirun -np N`。
- **编译也放进 sbatch**（登录节点不许跑重活）；`taskset -c 0` 在分配内会失败，别硬写核号。

### 2.4 编译器与工具（2026-09-21 实测）

| 工具 | 情况 |
|---|---|
| `g++` | **10.3.1**（ARM 计算节点），`-fopenmp` **实测可用** |
| `clang++` | **计算节点没有**；登录节点有 clang 12 但**没有 `omp.h`** → `clang++ -fopenmp` 直接失败 |
| `cmake` | 有，默认选 `/usr/bin/c++` = g++ 10.3.1（不由我们决定用哪个编译器） |
| `perf` | **任何节点都没有** → 热点定位靠"数调用次数 × 单次成本 + 分段计时 + 缩小规模" |
| 其他 | `gprof`/`gdb`/`strace` 有；`python3` 3.9.9，`pyyaml` 已装在 `~/.local`（家目录共享，计算节点也可见）；换账号若报 `No module named 'yaml'` 用 `pip install --user --force-reinstall pyyaml` |

→ **推论：不要赌 OpenMP 一定存在**。需要并行时用 `std::thread`（零依赖，约 30 行），
线程数按 `环境变量 > sched_getaffinity() > cgroup cpu.max > hardware_concurrency()` 决定，**不要硬编码 128**。

### 2.5 ★ 计时噪声：必须多次测量

实测（kp025/kp026）：**同一算例重复测可有 ±40% 抖动**，甚至"步数更少的 run 反而更慢"。

- **任何性能结论都要 ≥3 次取中位数**，不许用单次结果调参。
- 拿不到稳定数字时，先怀疑机器，再怀疑代码。
- 汇报时写清"几次测量的范围"，不要只写一个最好看的数。

## 3. 题目结构与测评流程

### 3.1 一道题的仓库长什么样

```
<NN>-<name>/
├── readme.md / README.md   ← 题面：【评分标准】【提交文件】【编译运行】
├── evaluate.py             ← 本地模拟判题（最重要的文件，逐行读）
├── submit.yaml             ← 只允许提交哪些文件（决定可改动范围）
├── submit.py               ← 一键打包成 submit.zip
├── download.sh             ← 拉数据（可能已失效，见 §3.4）
├── source_code/            ← 代码 + 数据（CMakeLists.txt / Makefile / compile.sh）
└── writeup.md              ← 你的解题报告（多半是计分项）
```

### 3.2 判题链路与隐藏约束

```
读 submit.yaml → 用你的文件替换原文件 → 编译（有超时！） → 跑测试算例（有超时！）
→ 解析 stdout / 结果文件 → 正确性校验 → 按耗时或指标算分 → 写 result.yaml
```

**必查的隐藏约束**（都在 `evaluate.py` 里，题面不一定写）：

- **编译超时**：见过 `timeout=120`；别引入 LTO/重量级模板，否则编译超时 = 0 分。
- **运行超时**：单算例几百秒到 2000 s 不等。
- **输出解析方式**：读结果文件还是**正则匹配 stdout**；格式必须完全对上，**别重定向或过滤 benchmark 输出**（有的题明确算违规）。
- **正确性阈值**：题面与脚本可能不一致 → **以脚本为准**，但按更严的留余量。
- **计时段在哪**：计时器加在哪几行，决定你优化什么（同时关系到规则 4，见 05 §1 规则 4）。

### 3.3 ★ 两种计分类型（决定"要做到多快就够"）

| 类型 | 特征 | 策略 |
|---|---|---|
| **A 达标型** | `evaluate.py` 里满分线是**源码常量**（如 `full=14.8s`、`1.4e9 TEPS`） | **达到满分线就停**，边际收益为 0；达标后留 20%~50% 余量防评测机差异 |
| **B 相对最优型** | 满分基准 = **所有选手中最优的提交**（从榜单/数据库读，动态） | **没有"够了"**，持续逼近物理上限；但按比例给分，不要为最后几个百分点冒正确性风险 |

今年（2nd）**两种都有**，所以每道题开工前先做这个判断。策略细节与物理上限估算见 `05` §5 与 `02` §6。

**曲线形状也要看**：很多题是对数曲线（越接近满分越难），意味着"稳"比"再快一点"重要。

### 3.4 ⚠️ 数据可能已经下线

`/lustre/share/xflops/` **整棵树已经不存在**（2026-09-21 实测：登录节点上 `/lustre` 只是空目录，计算节点连 `/lustre` 都没有）。

```bash
cat download.sh                                    # 看它从哪拷
ssh arm 'bash -lc "ls -la /lustre/share/xflops/"'  # 先确认存在
```

**应对**：

- 数据没了但题面给了格式 → **自造等价样例**：用**未修改的 baseline** 在**目标平台**上生成参考输出做对拍，并在 writeup 里写清楚。
- **数据是评测门禁**（必须先跑通某流程才评测后续部分）→ 这题**无法完整做**，早点和用户确认，别硬耗。
- **筛选规律：优先挑 `source_code/` 里自带 generator / 自带 server / 自带样例的题。**

## 4. 常见题型原型（两年 15 道题的归纳）

> 今年题面不同，但**原型**高度可复用。识别原型 → 直接套 `02` §4 的技巧卡（T1–T32）。
> **编号提醒**：本表的 A–J 是**题型皮编号**；`02` §3 的 A–E 是**瓶颈分类**（算法/吞吐/带宽/通信/工程），两套编号不要混用。

| 原型 | 识别信号 | 主攻方向（技巧卡） |
|---|---|---|
| **A 单核位运算 / 逻辑** | 题面说"仅分配 1 个 CPU 核心"，操作是位级或小数据 | 消除分支、SWAR/位切片、查表与递推（T6 T8 T14） |
| **B 计算密集（多核）** | 纯浮点/整数计算，数据小、算得多 | 编译选项 → 去热路径开销 → 向量化 → 多线程（T9 T10 T14 T15–T17 T18） |
| **C 带宽 / 内存密集** | 数据远大于 cache，算得少；加速比上不去 | 循环交换、分块、SoA、预取、非临时写（T11 T12 T8） |
| **D 通信 / MPI** | 有 `MPI_*` 调用、`mpirun`；多节点 | 减少消息条数、合并小消息、重叠通信与计算、换集合通信（T22–T25） |
| **E 工程 / 构建 / 脚本** | 分数在"流程对不对"而非"算得快" | 稳、可复现、不依赖环境细节；先跑通再换库换参数（T26–T28） |
| **F IO / 解析密集** | 时间花在读写与解析（`fscanf`/`getline`/HTTP） | 减少系统调用、批量读、自定义解析、mmap、连接复用（T29） |
| **G 图计算** | 题面含 BFS/SSSP/PageRank | direction-optimizing、位图 frontier、按度数重排、避免虚假共享（T11 T19 T20） |
| **H 物理 / 数值仿真** | `dt/tf` 参数、每步扫全场、长时间积分 | 常量表外提、消除每步分配、空间并行（**注意浮点顺序**）（T9 T10 T30） |
| **I AI / 量化 / 推理** | 出现 `quant`/`dequant`/safetensors | 内存带宽为王、融合算子、减少类型转换、C++ 扩展（T12 T26 T32） |
| **J 集群知识问答** | 选择题/填空题，考环境常识 | 直接在集群上 `which`/`module`/`scontrol` **实测**，别猜 |

**跨原型的行动顺序**（工程上最划算的顺序，不等于理论收益排序）：

```
编译选项(§5.1) → 热路径固定开销(§5.2) → 内存布局(§5.3) → 向量化(§5.4) → 多线程(§5.5) → 改算法(§5.6)
```

> ⚠️ 这个顺序容易和 `02` §10 的"能改算法就不要先改常数"混淆，两者并不矛盾：
> **工程顺序**是从"零风险、几乎白送"的收益开始摘果子（实测光 Debug→Release 就常常值 3 倍）；
> **同时**要始终保留一个念头——这道题是否存在**数量级的算法级机会**（`02` §1 的 5 个问题里的 ①）。
> 如果 ① 的答案是"存在"，那就先改算法，别在常数上磨。

## 5. 优化手段速查

> 通用技巧卡（含适用信号 / 风险 / 验证方法）在 `02` §4；这里放**实测过、有效**的具体手段。

### 5.1 第 0 层：编译与构建（永远先做这一步）

```cmake
set(CMAKE_BUILD_TYPE Release)                    # 官方 CMakeLists 常见陷阱：写死 Debug（只有 -g）
set(CMAKE_CXX_FLAGS_RELEASE "-O3 -DNDEBUG -pthread -ffp-contract=off -fno-math-errno")
```

- `-O3`：先用上，几乎是白送的（实测 09 题 Debug→Release 就是 **3.2×**）。
- **`-ffp-contract=off`：只要结果要和参考实现比，就必须加。** gcc 默认 `fast` 会做 FMA 合并，浮点结果就变了。
- **`-ffast-math` / `-Ofast`：禁用。** 会重排/近似浮点，长步数积分与分段力场必然分岔。
- **`-march=native` / `-mcpu=native`：默认禁用。** ① 会改 `pow` 等 libm 的舍入（**实测让某题 6 个测试点全挂**）；
  ② 编译机与判题机 CPU 不同会直接 SIGILL。要用就用保守档或做运行时派发。
- `-DNDEBUG` 会让 `assert` 消失——若参考实现依赖 `assert` 的副作用，语义会变。
- 需要线程时先确认判题环境有 OpenMP；没有就用 `std::thread`（见 §5.5）。

### 5.2 第 1 层：热路径的固定开销（常常比向量化还值钱）

- **热路径上的 `new`/`delete`/`malloc` 一律提到外面**：实例——每节点每步 `new double[1348*4]`
  （43 KB × 184 万次）。改成**每线程一份常驻缓冲区**。
- **循环不变量外提**：常量表、单位向量、`sin/cos(mφ)`、递推表。典型收益 2×，且**零数值风险**。
- **消除重复计算**：同一量在多个循环里重算（每面重新归一化顶点、每次访问都做 `double→int` 转换）。
- **函数内联**：把 `assert` 满天飞、局部变量一堆的"每元素调用"内联进循环。

### 5.3 第 2 层：内存与访存

- **数据布局**：SoA vs AoS 按访问模式选；把跳着读的列主序改成连续读。
- **分块（tiling）**：让工作集落进 L1/L2。矩阵乘、stencil 必用。
- **预计算常量索引**：把"以 double 存储的下标"提前转成 `int` 数组。
- **位压缩**：位图表示集合；一个 `uint64` 的多个位平面同时服务多个计数器（bit-slicing）。
- **避免虚假共享**：多线程各写同一 cache line 的不同元素 → 性能崩塌（实测 **128 线程比 1 线程慢 10 倍**）。
  每个线程的累加器/计数器**独占 cache line**（padding 到 64B）。

### 5.4 第 3 层：向量化

- 先让编译器自动向量化：`-O3` + 消除别名（`__restrict__`）+ 对齐 + 简单循环体。
- **`sqrt`/`log`/`atan2` 这些 libm 调用不会自动向量化**（x86 有 libmvec，**本集群 ARM 的 glibc 2.34 没有**）。
  手写向量化 `log`/`atan2` 可以再拿 1.5~2 倍，但引入约 1e-8 的相对误差，
  在长步数/分段力场里**可能分岔**——性价比自己判断。
- 宽度：NEON 是 2 路 double / 4 路 float，AVX2 是 4 路，AVX-512 是 8 路。
- 平台相关代码用 `#if defined(__aarch64__)` 包住并留标量 fallback，否则本地（x86）无法验证。

### 5.5 第 4 层：并行

**先判断依赖**——这是最重要的一个问题：

```
同一个时间步/同一轮迭代里，各元素之间有没有依赖？
  没有（只读同一份旧状态）→ 按下标跨步分给各线程，结果与线程数无关（精确并行）
  有（需要浮点归约）      → 改归约顺序会改结果 → 换一根并行的轴，或保持原顺序做树形归约
```

- **手写线程池 vs OpenMP**：判题机编译器不确定时用 `std::thread`（~30 行，零依赖）。
- **线程数不要硬编码**：`环境变量 > sched_getaffinity() > cgroup cpu.max > hardware_concurrency()`，
  否则判题机只给 8 核时你会开出 128 个线程自相残杀。
- **屏障是 128 核上的真瓶颈**（三代实现实测，极具教学价值）：
  - 主线程**串行轮询 127 条远端 cache line** → **437 µs/次**；
  - 全核**自旋在同一条 line** 上 → **1913 µs/次**（比前者更糟，一致性流量打满互联）；
  - **分组完成计数器（每组独占 cache line）+ aarch64 `wfe/sev`** → **4.31 µs/次**。
  - 坑：`wfe` 等待的**每一个**写都必须跟一条 `sev`，漏一个就会睡到下一个时钟中断。
- **减少同步次数**：融合阶段、乒乓缓冲代替整块拷贝，把每步 3 次屏障降到 1 次。
- **亲和性与 NUMA**：128 核常见多路 NUMA，跨 socket 访存很贵；用 `OMP_PROC_BIND`/`OMP_PLACES` 或自行按 NUMA 分块。2 的幂的线程数通常更快。

### 5.6 第 5 层：算法与数据结构

- 前缀和/预计算、分块、哈希去重、环形缓冲、流水线（HTTP 批量请求）、位切片计数、SWAR、`popcount`、XOR 折叠做快速不等判断。
- **只在数学上等价且不改变浮点结合顺序时**才改算法；否则先做 §5.1~§5.5。

### 5.7 第 6 层：IO 与解析

- 批量读（一次读大块）、并行读、`mmap`、自定义解析器替代 `fscanf`/`getline` 逐字段。
- 输出也要省：`fprintf` 逐字段在热路径上是灾难；先攒到缓冲区。
- 网络题：**连接复用（keep-alive）+ 批量请求**是吞吐关键；注意别把计算挪进"预取线程"（违反规则 4）。

### 5.8 MPI

- 消息**条数**通常比消息**大小**更致命；小消息合并，用集合通信（`Bcast`/`Allgather`/`Reduce`）替代手写循环。
- 小规模问题（几百万边 / 几十 MB）**单机共享内存往往完胜 MPI**——先算规模再选架构（实测某图题参考实现的 MPI+AML 单进程只有 4e7 TEPS，整图放共享内存后高一个数量级）。
- 集群上 MPI 必须 `sbatch` + `mpirun`（`srun` 起不了 OpenMPI）。

## 6. 容易出错的地方（Top 20，逐条都真踩过）

**A. 数值正确性**

1. **参考文件是平台相关的**：不同平台的 libm（`pow`/`sin`/`log`）结果不同，
   同一份代码在 x86 与 ARM 上会给出不同的"正确"答案 → **ref 必须在目标平台上生成**。
2. **`-march=native` 改变 `pow` 的舍入** → 测试点全挂。别用。
3. **FMA 合并（`-ffp-contract`）改变结果** → 必须显式 `-ffp-contract=off`。
4. **重排浮点归约顺序**（并行归约、循环交换、对称化）会改结果 → 要么保持顺序，要么确认容差足够。
5. **分段/接触类仿真的分岔放大**：1e-16 的舍入差会在"是否接触"的判定点被放大成 0.1 量级。这是物理决定的，不是 bug → **保持运算顺序 + 留足容差余量**。
6. **重写热循环前必须抠清原语义**：曾经因为"循环结束后某个临时变量保留的是第 3 个顶点而不是第 1 个"这种细节，差点把等价改写写成不等价。

**B. 性能测量**

7. **单次计时不可信**（±40% 抖动）→ ≥3 次取中位数，并写清范围。
8. **忘记 `make clean` / rsync 带过去旧 `.o`** → `make` 说"无需做任何事"，跑的是旧二进制，白等一轮。benchmark 脚本第一步必须重编并打印编译结果。
9. **`perf` 不存在** → 别浪费时间找；用"数调用次数 × 单次成本 + 分段计时 + 缩小规模"。
10. **计时包含初始化**：有的题整个进程计时（含读文件），初始化 1 s 在 5 s 目标里就是 20% → 先单独量一次"空跑"的时间。

**C. 集群与作业**

11. **不要在登录节点跑重活**（编译大工程 / benchmark）→ 有封号风险。
12. **`--mem` 写大了会变成更多 CPU** → 撞 QOS 上限；默认 1950 MB/核就够了。
13. **OOM 会导致"没有输出"** → 判题看到缺输出直接 0 分。
14. **残留作业占满 QOS 单作业名额**（`MaxJobs=1`）→ 提交前 `scancel -u $USER` + `squeue -u $USER`。
15. **`sinfo | head` 截断分区列表** → 误判"队列消失"。用 `scontrol show partition` 看全量。
16. **`srun` 起不了 OpenMPI** → 用 `sbatch` + `mpirun`。

**D. 提交与流程**

17. **`writeup.md` 是计分项**：缺了或与代码对不上 = 该题 0 分。**中途就开始写，不要留到最后**（结构见 §7.2）。
18. **提交包要自检**：跑 `submit.py` 后**打开 zip 看清单**是否正好是 `submit.yaml` 列的那些文件（改了清单外的文件 = 白改）。
19. **输出格式必须精确匹配**：判题可能是正则解析 stdout，空格/字段名错了就解析不到 → 0 分。
20. **别把大文件/二进制提交进 git**：曾误提交 1.7 GB 测试数据把 `.git` 撑到 458 MB。提交前 `git status`，给 `dev/`、`build/`、产物加 `.gitignore`。

## 7. 交付标准

### 7.1 代码

- 只改 `submit.yaml` 允许的文件；**提交前用 `git status` 确认改动范围**。
- 如果允许改的文件里没有你想改的那个文件（如某个 `.cpp`），可以在**允许改的文件**里写自己的实现去替代调用它
  （例：某题不允许改 `SurfacePoints.cpp`，就在 `acceleration.cpp` 里写一份内联版本替代）。
- 可读、有注释，能讲清"为什么这么做"。

### 7.2 writeup.md（计分项）

```
1. 一句话总结（最终成绩 + 核心手段）
2. 题目在算什么 / 数据规模
3. 环境与工具（编译器、集群、队列、测量工具）
4. baseline 实测（原始代码跑出来多少）
5. 热点定位（怎么找到的，不是"我觉得"）
6. 优化清单：逐条【原理 + 收益 + 风险】，每条都能独立看懂
7. 正确性验证（对拍方法 + 实测误差）
8. 实测结果（≥3 次的表格，含环境说明）
9. 踩坑与陷阱（这一节最有价值）
10. 还能更好的方向（没做的 + 为什么不做）
11. 可迁移的经验
```

### 7.3 正确性三层验证法（强烈建议照做）

```
第 1 层：用【未修改的原源码】+ 同样的编译选项跑一遍，留底
第 2 层：拿自己的版本与它【逐位对比】→ 证明"重构没有引入数值差异"
第 3 层：再与官方参考文件 / 官方 hash 比 → 证明"结果本来就是对的"
```

只有第 2 层通过，才能说"我的改写是等价的"；否则一旦结果不对，你分不清是改写的锅还是编译选项的锅。

## 8. 标准作业流程（SOP 速查卡）

```bash
# 0) 侦查
cat <题>/readme.md                      # 评分标准 + 提交文件
cat <题>/submit.yaml                    # 能改什么
cat <题>/evaluate.py                    # 怎么算分 / 计时 / 解析输出
cat <题>/download.sh; ssh arm 'bash -lc "ls -la <数据路径>"'   # 数据还在吗

# 1) baseline：用原封不动的源码跑一次，记下耗时、正确性锚点、编译选项

# 2) 判断计分类型：满分线是常量 → 达标型（达标就停）；动态/榜单 → 相对最优型（持续优化）

# 3) 找热点：数调用次数 × 单次成本；分段计时；缩小规模
#    顺序：编译选项 → 热路径固定开销 → 内存布局 → 向量化 → 多线程 → 算法

# 4) 每改一步就对拍（§7.3 三层验证法）

# 5) 集群实测（sbatch，≥3 次取中位数）
rsync -az -e "ssh -o ControlMaster=no -o ControlPath=none" ./source_code/ arm:<work>/source_code/
ssh arm "bash -lc 'squeue -u \$USER; cd <work> && sbatch job.slurm'"
ssh arm "bash -lc 'squeue -u \$USER; tail -30 <work>/slurm_*.out'"

# 6) 收尾
python3 submit.py <stage>               # 打包
python3 -c "import zipfile;[print(i.filename) for i in zipfile.ZipFile('submit.zip').infolist()]"
git status --porcelain                  # 确认只改了该改的、没混进大文件
git -c user.name="ygtqtree" -c user.email="ygtqtree@local" commit -m "<type>(<题号>): <做了什么>（<实测数字>）"
```

**汇报给用户时要说清**：实测数字（几次测量）、估算得分、已验证 vs 未验证、卡在哪里。

## 10. 最后：三条最值钱的经验

1. **先看编译选项，再看代码。** 最便宜的收益都来自"把 Debug 改成 `-O3`（并加 `-ffp-contract=off`）"，
   比任何算法改写都划算。可提交文件清单里出现 `CMakeLists.txt`/`compile.sh`，就是出题人在提示这一点。
2. **算"调用次数 × 单次成本"，不要等 profiler。** 没有 `perf` 也能定位热点：
   数循环层数、数 `sqrt/log/atan2` 次数，乘以元素数和步数，十分钟就能算清楚。
3. **并行前先问"迭代之间有没有依赖"，并行方案要选判题机上一定存在的那个。**
   前者决定能不能精确并行（实测某仿真题答对了 → 128 核 111×，87% 效率），
   后者决定代码会不会在判题机上直接编译失败（clang 没有 `omp.h` → 用 `std::thread`）。

## 11. 附录：两年 15 道题提炼出的 6 条硬结论

> 15 道题的逐题小结已删（题目下线、细节只在各自 `writeup.md` 里有意义）；
> 这里只留**换一道新题仍然成立**的部分。仓库里的 writeup 是最有价值的原始素材。

1. **"1 核 / 4 核 / 8 核 / 32 核 / 128 核"是一条固定的难度阶梯**：核数一给出来，题型与优化轴基本就定了。
   单核只能挤位运算/分支；多核先想并行；**128 核时"并行效率"本身就是考点**（屏障、NUMA、亲和性）。
2. **同一原型反复出现**：位运算、MPI 集合通信、物理仿真、图计算、网络 IO、AI 量化。
   今年换皮不换骨——先归类（§4），再动手。
3. **"编译选项"这一层的收益被严重低估**：某题光 Debug→Release 就是 3.2×；
   另一题因为 `-march=native` 直接全挂。**先动编译选项，再动代码。**
4. **最大的性能坑往往不是算法，而是"热路径上的固定开销"**：每步 `new`、每元素重算常量、每元素重复归一化。
   这类改写**零数值风险**，性价比最高。
5. **同步原语在大核数下会反噬**：屏障三代实测（437 µs → 1913 µs → 4.31 µs）说明"线程更多 ≠ 更快"。
   **核数超过 32 之后，先把同步与访存算清楚。**
6. **数据可用性要第一时间确认**：15 道题里有 4 道依赖 `/lustre/share/xflops/`，而该目录**整棵树已下线**；
   其中 2 道靠自造等价样例绕过，2 道因"数据即门禁"直接报废。
   → **优先挑自带 generator / 自带 server / 自带样例的题**（§3.4）。
