## 0. 铁律（违反任何一条，做了也白做）

1. **正确性不过 = 0 分**。任何改动后先过正确性门禁，再谈时间。
2. **只改允许改的文件**（`submit.yaml` 为准），其余文件评测时会被替换成官方副本。
3. **不打表**：不硬编码样例答案、不依赖特定随机种子/数据分布、不读 `ref*` 反推答案；判题方会改算例。
4. **不得把计算挪出计时段**：不能用异步/后台线程/全局构造/跨调用缓存，
   把本该在计时区间内完成的计算提前、延后或挪走。判据："把计时段内的代码换成 `sleep`，结果还对吗？"
5. **先测量后优化**：没有基线数字的优化都是盲猜；一次只改一个变量。
6. **能回退**：每次有效改动前留快照（`git commit` 或复制文件），性能题"越改越慢"是常态。
7. **不猜评测**：编译/运行命令、超时、判据、计分一律从 `evaluate.py` 读，不从题面猜。
8. **只在计算节点跑重活**：并行编译/并行计算/基准测试一律走 `sbatch`（登录节点违规会封号）。文本文件保持 **LF**。
9. **提交可读的原始源码**：赛后要 Code Review，禁止混淆/编译产物；AI 可以用，但每一行都要能解释。

> 完整规则、逐条 ✅/❌ 示例、自查清单：`05_比赛规则与红线.md`。

## 2. 瓶颈定性（决定后面所有选择）

```
是"编译/配置/调参"类任务？
 ├─ 是 → 【E 工程型】→ 先跑通，再换最快的库，再扫参数
 └─ 否 → 测 2~3 个规模点的时间斜率
          ├─ 斜率 > 1（近 n²） → 【A 算法型】→ 换算法/用对称性/把求解变成排序或扫描
          └─ 斜率 ≈ 1 → 看单位计算的访存量
                 ├─ 访存 >> 计算 → 【C 带宽型】→ 减少遍历遍数、位压缩打包、分块、换布局
                 └─ 计算 >> 访存 → 【B 吞吐型】→ SIMD + 多核 + 拆依赖链
          ※ 涉及多进程 → 叠加【D 通信型】→ 减少消息条数、聚合、重叠、改分解
```

**技巧索引（卡全文见 `02` §4）**

- **A 算法**：T1 降复杂度 · T2 对称/剪枝 · T3 贪心交换论证（得排序键）· T4 排序即原语（计数/基数）· T5 前缀和/一次扫描 · T7 分治分块
- **B 吞吐**：T9 去 sqrt/除法、Horner · T10 拆依赖链（多累加器）· T14 给编译器递信息 · T15/T16/T17 向量化（自动/手写/选 lane 维度）· T13 分支消除
- **C 带宽**：T8 位压缩打包 · T11 循环交换与分块 · T12 AoS→SoA/对齐/padding · T4 线性排序
- **D 通信**：T22 域分解（数据量小就直接 Bcast/Allgather）· T23 聚合消息（减条数 > 减字节）· T24 计算通信重叠 · T25 集合通信选型
- **E 工程**：T26 换库/换 BLAS（最大杠杆）· T27 编译选项 · T28 参数搜索（注意"只允许一组参数"）
- **横切**：T18 并行原语归类（map/reduce/scan/histogram/sort/stencil）· T19 调度与负载均衡 · T20 亲和性/伪共享/NUMA · T30 误差预算 · T31 等价变形 · T32 精度换速度

**动手顺序（工程上最划算，非理论收益排序）**：编译选项 → 热路径固定开销 → 内存布局 → 向量化 → 多线程 → 算法。
**同时**必须回答"算法层是否存在数量级机会"——若有，先改算法（`02` §1 的第 ① 问）。

**同时必须算"上限"**：`核数×主频×每周期浮点操作数`、`数据量/带宽`、Amdahl。
结论只有两种：**"还有 10×，继续"** 或 **"只剩 1.2×，收手换题"**。

## 3. 正确性协议（每次改动后必跑）

**三层防线**：① 小规模对拍（保留朴素实现，随机小数据自动比对）② 不变量/守恒量 ③ 泛化回归（全部给定算例 + 多随机种子）。
**三层验证法**（写进 writeup，见 06 §7.3）：未改源码留底 → 与自身版本逐位对比 → 与官方参考对比。

**浮点重排决策（数值题的生死线）**

```
要改变浮点运算顺序（并行归约/向量化/对称化/分块）？
 ├─ 判据是精确相等 → 禁止重排
 └─ 否 → 相对容差 = 允许偏差 / 答案量级
          ├─ ≫ 1e-12 → 可重排，但必须全算例回归
          └─ ≲ 1e-12 → 不要重排数值核心；改为并行"互不影响的维度"（如按个体并行、保持个体内部顺序）
                       或先提高精度（double / 补偿求和）
 ※ 迭代·混沌·长时间积分：误差指数放大 → 只能实测最坏算例，不能推公式
```

**边界清单**：n=0/1/2；非整倍数（不整除进程数/向量宽度）；非对齐；负数/零/极大极小；重复元素；全相同；退化输入；溢出边界；NaN/Inf。

## 4. 测量协议

- 与评测**同命令、同计时区间、同环境变量**；第一遍只热身（warmup）。
- **重复 ≥3 次，报告 min 或中位数**（本集群实测同一算例可有 **±40% 抖动**，单次结果不可用）。
- 指标趋势不可信时先怀疑：频率漂移、别的作业干扰、cache 冷热、**编译器把被测代码优化没了**。
- **`perf` 在集群任何节点都没有** → 用"数调用次数 × 单次成本 + 分段计时 + 缩小规模"，
  辅以 `gprof`/`gdb`/`strace`。
- 排查前先确认自己**跑的是刚编译的二进制**（`make clean` / 重新编译并把编译输出打印出来）。

**记录格式（每次实验追加一行，最终进 `writeup.md`）**

```
| 时间 | 版本/说明 | 编译 | 正确性 | 指标 | best/中位数 | 结论(KEEP/REVERT) |
```

## 5. 分数策略（按公式形状分配精力）

| 公式形状 | 策略 |
|---------|------|
| 线性插值 | 中档优化就有中档分，持续迭代划算 |
| 对数插值 | 越接近满分越难，做到"良好"就收手 |
| 反比型 | 时间越小涨分越快，冲第一档收益大 |
| 阶梯/档位 | 跨越一档是固定收益，专攻"下一档"的瓶颈 |
| 达标制（跑通给分） | 最先拿，再谈性能 |

**★ 先分清两种计分类型（今年新规则，详见 `05` §5）**

- **达标型**（`evaluate.py` 里满分线是**源码常量**）：达到阈值 + 留 20%~50% 余量即收手，多出的性能不加分。
- **相对最优型**（满分 = 榜单/数据库里的全场最优）：没有"够了"，要持续逼近物理上限；
  但按比例给分 → 接近最优也有大部分分，**不为最后几个百分点冒正确性风险**。

**通用节奏**：侦察 10% → 保底（跑通/小算例/达标分）20% → 主攻 1~2 题 50% → 收尾（回归/打包/writeup）20%。

## 7. 环境速查（最常踩的坑；完整实测见 `04`）

- 连集群：`ssh arm 'bash -lc "..."'` —— **必须 `bash -lc`**，否则没有 `module` 命令。
- **队列名会变**：`scontrol show partition | grep PartitionName` 现探（2024 题面里的 `kp920race`/`kp920vscode` 早已消失）。
  2026-09-21 实测：`kp_run` 有 23 个 idle（128 核 / 2h）可用；`arm128c256g`/`debugarm` 常年 drain。
- 提交：`-p <分区> -q <同名QOS> -A acct-stu` 都要写；**不要写 `--mem`**（默认 1950 MB/核，
  写大了会折算成更多 CPU 撞 QOS 上限）；`kp_run` **MaxJobs=1** → 提交前先 `scancel -u $USER`。
- **`srun` 起不了 OpenMPI** → MPI 用 `sbatch` + 脚本内 `mpirun -np N`。
- 编译器：ARM 计算节点只有 **g++ 10.3.1**（`-fopenmp` 可用），**没有 `clang++`**；
  登录节点的 clang 12 **没有 `omp.h`** → **不要赌 OpenMP**，需要并行用 `std::thread`（零依赖，线程数用 `sched_getaffinity()` 探测，别硬编码）。
- **`perf` 没有**（登录/计算都没有）；`gprof`/`gdb`/`strace` 有。
- Python：3.9.9，`pyyaml 6.0.3` 装在 `~/.local`（家目录共享，计算节点也可见）；若报 `No module named 'yaml'` 用 `pip install --user --force-reinstall pyyaml`。
- 同步坑：`rsync` 会把本地 `*.o`/`build/` 带到集群 → `make` 说"无需做任何事"。先 `make clean`。
- 平台相关代码（`arm_neon.h`、intrinsic）用 `#if defined(__aarch64__)` 包住并留标量 fallback。

## 8. 交付前必须做到

- [ ] 正确性门禁全绿（**全部**给定算例，不只样例）；
- [ ] 有 baseline 与最终指标的可比数字（同命令、同口径、**≥3 次**）；
- [ ] `writeup.md` 已写（**计分项**，结构与要求见 `06` §7.2）：要求、为什么慢、优化推理、关键代码讲解、实测数据、工具命令、踩坑、复现命令、还能更好的方向；
- [ ] 按 `submit.yaml` 核对文件清单，`python submit.py` 打包并**打开 zip 核对**；
- [ ] 明确说明"哪些结论是本地验证的、哪些必须在集群复测"。

## 9. 什么时候停止

- 达标型已达标（或边际收益递减、只剩 1.2× 空间）→ 换题；
- 某个工具/库卡住超过预算 → 换等价路线（换库/换算法/换实现），别死磕；
- 数据不可用且是评分门禁 → 早点和用户确认，不要硬耗；
- 距结束不足 10% 时间 → 只做提交与校验，不做大改动。

## 10. 红线（用户与评测方都会看）

不合作作弊、不攻击评测、不打表、不在登录节点跑高负载、不把计算挪出计时段、
**AI 可以辅助但必须能解释提交的每一行代码**。不要为了跑分留下无法解释的代码。
