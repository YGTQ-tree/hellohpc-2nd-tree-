# 05 · 比赛规则与红线

> 来源：HelloHPC 2nd 比赛页 <https://xflops.sjtu.edu.cn/oj/contests/hellohpc-2nd> 的「比赛规则」（用户提供的截图，共 8 条）。
> 用途：**开工前读一遍，提交前对照自查**。AI agent 尤其要读——很多"聪明"的优化正好踩在红线上。
> 本文档是**规则唯一权威**；`06_作答总指南.md` §1 只放摘要，`03_竞赛解题Skill.md` 只放可执行条款。
> 相比 2024 年旧规则，新增**第 4 条（禁止把计算挪出计时段）**与**第 8 条（Code Review / 禁止混淆代码）**。

---

## 0. 一句话总结

> **可以变快，不可以作弊；可以问 AI，不可以不懂；可以并行，不可以把活挪到计时之外。**

## 1. 八条规则逐条解读

### 规则 1 · 不得作弊（个人赛 + 代码查重）

> 原文：不得作弊。比赛为个人赛，任何多人合作完成题目的行为都将被认为作弊。我们将进行代码查重，希望大家诚信参赛。

- ✅ 自己写、自己改、自己理解；查资料、问 AI、看开源实现都行
- ❌ 和别人分工一人一题；互相传代码；照抄别人的 `submit_func.c` / `solver.hpp`
- ⚠️ **对 AI agent 的额外提醒**：如果多个参赛者用同一个 agent、同一套提示词，产出的代码会高度相似 →
  **可能被查重系统判定为雷同**。务必自己重写关键部分、加自己的注释与变量名，并能解释每一行。

### 规则 2 · 不得攻击评测与 OJ

> 原文：不得使用恶意代码注入等方式对评测与 OJ 进行攻击。本比赛不是 CTF，不考察任何形式的攻击。

- ✅ 正常提交、正常查询排行榜
- ❌ 构造恶意输入让评测脚本崩溃/超时；伪造评测结果；扫描/攻击 OJ 接口；篡改 `evaluate.py` 让它给高分
- ⚠️ 本地**可以**为了开发方便另存一份 `evaluate.py` 改资源校验（例如本机没有 128 核），
  但**绝不能**把它当成提交物，也不要试图影响线上评测。

### 规则 3 · 不得打表

> 原文：不得打表。超算比赛要求保证优化后源码的正确性与普适性。如果我们发现你的代码中基于给出的示例算例打表，将取消参赛成绩。同时我们在评测时会适当修改示例算例中的部分数据。

- ✅ 通用的算法优化；对**任意合法输入**都正确
- ❌ 把样例答案硬编码进代码；按输入大小/种子分支返回预设结果
- ❌ 依赖给定数据的具体分布（例如"粒子一定均匀分布"）来跳过计算
- ❌ 读取题目自带的 `ref*.data` / `std_ans` 来反推答案
- ❌ 跨调用缓存/记忆化（第二次调用同一输入直接返回上次结果）——同时也违反规则 4
- ⚠️ 常量表（如 256 项的位反转表）是**通用**的，允许；与**具体输入数据**相关的缓存/记忆化不允许。

### 规则 4 · 不得用异步等手段把计算挪出计时段 ⭐（新规，最容易被误踩）

> 原文：使用计时计算性能的题目均给出了明确的计时阶段，不得通过使用编程语言的异步等特性将原处于计时段的计算过程移动到计时段外以减小运行时间。

**先搞清楚"计时段"在哪**：每题都不一样，**必须去本题的 `evaluate.py` / `main` 源码里确认计时器加在哪几行**。
下面这张表只是 2024 年五题的实测结果（题目已下线，留作"计时段可能长什么样"的示例）：

| 2024 样例题 | 计时段 | 判断依据 |
|------------------|--------|---------|
| Bithack | `rotate_the_bit_vector()` 一次调用的 **CPU 时间** | `ktiming_getmark()` 包住这一次调用 |
| Clever_Clang | `gradient_descent()` 一次调用 | `main.cpp` 的 `steady_clock` 包住它 |
| Cluster | `solve()` 一次调用 | `main.cpp` 的 `TIC(0)/TOC(0)` |
| N_Body | **每一步**里 4 个函数之和，累加 1002 步 | `omp_get_wtime()` 写在循环体内 |
| HPL | 整个 `xhpl` 运行（由 Slurm 计时） | `sbatch` 的墙钟时间 |

**❌ 会被认定为违规的写法**

```c
// ❌ 在计时段外起一个后台线程/异步任务，把真正的计算提前或延后做完
std::thread t([]{ heavy_precompute(); });     // 计时开始前就开跑
t.detach();                                    // 计时段内"看起来"很快

// ❌ 把与输入相关的计算挪到初始化/构造函数/静态初始化里（那不在计时段内）
static bool inited = (precompute_all(), true); // 全局构造在 main 之前完成

// ❌ 把结果缓存到文件/内存，第二次调用直接返回（跨调用记忆化）
if (cache.count(input)) return cache[input];

// ❌ 在计时结束后继续算，只把"启动"算进计时段
start_timer(); async_launch(); stop_timer(); wait_for_result();

// ❌ 把计时段内的函数体掏空，改到"别的地方"算（哪怕还在同一次运行里）
```

**✅ 允许的做法**

```c
// ✅ 真并行：多线程/向量化，只要计算**确实在计时段内完成**
#pragma omp parallel for
for (...) { ... }                     // 计时区间内真算，只是更快

// ✅ 算法级优化：更好的复杂度、更少的内存访问、SIMD
// ✅ 编译选项优化（在题目允许的范围内；有的题固定了编译选项就不能改）
// ✅ 常量表/常量折叠：与具体输入无关的预计算
// ✅ 把计算挪到**另一个仍被计时的函数里**（因为那一整个区间都在计时）
```

**一句话判据**：问自己——**"如果评测把计时段内的所有代码都替换成 `sleep(1)`，我的结果还对吗？"**
如果答案是"不对/没算"，那你就把计算挪出去了。

> 🔍 典型陷阱：某题的 `main` 里只有少数几个函数被计时，而 `main` 的初始化阶段不计时，
> 于是很容易想把"预计算"塞进初始化——**这就是违规**。
> 而且 `main` 往往属于"一定不可修改"的文件，评测时会换回官方副本（改了也白改）。

### 规则 5 · 可以使用 AI 辅助（但要按「Agent 辅助答题」的说明来）

> 原文：可以使用搜索引擎与 AI 辅助答题，具体支持与资源见「Agent 辅助答题」。

- ✅ 用搜索引擎、用 AI 写代码/查资料/解释报错/生成测试
- ℹ️ 用户于 2026-09-23 确认：「Agent 辅助答题」没有额外限制。此项是用户提供的确认，
  并非我们独立读取了需登录的 OJ 页面；若用户后续收到官方更新，以官方新说明为准。
- ⚠️ 旧规则里的要求仍然适用：「请确保自己已经充分理解了所提交的每一行代码的含义」——
  比赛结束后还要 Code Review（见规则 8），**你解释不了 = 说不清 = 有风险**。

### 规则 6 · 登录节点不得跑高负载

> 原文：请不要在登录节点上运行并行编译或并行计算等高负载程序。交我算平台设有相应检测，如因在登录节点上进行运行高负载程序导致封号后果自负。

- ✅ 在登录节点上：编辑文件、`rsync`、**单线程编译**、看日志、`sbatch` 投作业
- ❌ 在登录节点上：`make -j` 并行编译、跑 128 核程序、跑基准测试、长时间挂 VSCode 一大堆插件
- ✅ 正确姿势：`sbatch`（推荐）/ `salloc` / `srun`，写法见 `04_环境交接与工作区状态.md` §4
- ⚠️ **对 AI agent 的提醒**：agent 很"手快"，容易顺手就在登录节点上 `./prog` 跑一把。
  **任何"跑程序测性能"的动作都必须走 Slurm。**

### 规则 7 · 账号只用于本次比赛

> 原文：比赛分发的交我算账号仅用于参加本次比赛，请勿滥用交我算平台计算资源，一经发现，立即封号。

- ✅ 用比赛的账号做比赛的题（以及合理的练习）
- ❌ 拿它跑自己的项目、挖矿、长期占节点、开无关的常驻服务
- ⚠️ 提交作业时**别申请超出需要的资源**；测完及时 `scancel`；不要 24 小时挂着交互式会话。

### 规则 8 · Code Review：必须提交可读的原始代码

> 原文：比赛结束后组委会将进行 Code Review，如发现违规行为将进行处罚，排行榜名次可能发生变动。请确保你上传的代码是开发的原始代码，严禁上传编译后/混淆后的代码阻碍 Code Review。恶意阻碍、拒不配合 Code Review 者将被取消参赛成绩。

- ✅ 提交**手写的、可读的**源码；保留注释、合理的变量名、必要时的 git 历史
- ❌ 上传混淆过的代码、把关键逻辑塞进二进制/大数组、用宏把代码变成天书、拒绝解释
- ✅ **对 AI agent 的正面用法**：让 agent 顺手产出 `writeup.md`（每题一份），正好满足"能解释清楚"的要求
- ⚠️ 建议每次有效改动都 `git commit`，Code Review 时能拿出开发过程

## 2. 违规后果一览

| 违规 | 后果 |
|------|------|
| 多人合作 / 抄袭 | 取消成绩（代码查重） |
| 攻击评测 / OJ | 取消参赛成绩 |
| 打表 | 取消参赛成绩 |
| 把计算挪出计时段 | 视为作弊（成绩取消/处罚，新规明确禁止） |
| 登录节点跑高负载 | **封号**（后果自负，且账号是比赛发的） |
| 滥用平台资源 | **封号** |
| 上传混淆代码 / 阻碍 Code Review | 取消参赛成绩 |
| 不遵守「Agent 辅助答题」条款 | 按该条款处理（**待确认**，见 §6） |

## 3. 自查清单

**开工前**

- [x] 用户已确认「Agent 辅助答题」没有额外限制；常规比赛规则仍须遵守。
- [ ] 已确认本题的**计时段**在哪（自己读 `evaluate.py` / `main`，不要照抄 §1 的表）；
      已确认哪些文件**允许修改**（不许改的文件评测会替换）
- [ ] 已确认本题是**达标型**还是**相对最优型**（见 §5）

**每次优化**

- [ ] 这个改动只是"算得更快"吗？有没有把工作挪到计时段之外？
- [ ] 有没有引入与**具体输入数据**相关的缓存/记忆化/打表？
- [ ] 如果多个参赛者用同样的 AI 提示词，我的代码会不会和别人雷同？（→ 自己重写 + 加注释）
- [ ] 我能不能解释这段代码的每一行？（Code Review 会问）

**跑测试**

- [ ] 所有重活都通过 `sbatch`/`srun` 在计算节点执行（没有在登录节点跑并行程序）
- [ ] 没有乱写 `--mem`（会折算成更多 CPU，撞 QOS 上限，见 04 §4）
- [ ] 跑完 `scancel` 掉不需要的作业

**提交前**

- [ ] 提交的是**可读的原始源码**（不是编译产物、不是混淆代码）
- [ ] 每道题都有 `writeup.md`：优化思路 + 使用的工具 + 实测数据 + 踩过的坑
- [ ] 代码里没有硬编码的样例答案、没有读取 `ref*` 反推结果
- [ ] 用 AI 的部分，我能逐行解释（并且遵守了「Agent 辅助答题」的要求）

## 4. 与 2024 旧规则的差异

| 条目 | 2024 校内赛题面 | 现在（HelloHPC 2nd） |
|------|--------------|-----------|
| 打表 / 登录节点 / 不攻击评测 | 禁止 | 禁止（不变） |
| AI 使用 | "可以使用，但请确保理解每一行" | 可以使用，**但要看「Agent 辅助答题」的具体条款** |
| 把计算挪出计时段 | *未提及* | **明确禁止**（规则 4） |
| Code Review | 未提及 | **明确要求**（规则 8），禁止混淆代码与编译产物 |
| 账号用途 | "请勿滥用" | "仅用于本次比赛，违规即封号" |

> 拿旧题练手时，**主动按更严的现行规则执行**（不在登录节点跑程序、每题都写 writeup、
> 不使用任何与输入相关的缓存），这样正式比赛时不会有习惯性违规。

## 5. ★ 两种打分方式与对应策略

> **这是决定"什么时候收手"的关键信息，每道题开工前必须先确认它属于哪一类。**

| 类型 | 满分线 | 典型特征 | 策略 |
|------|--------|---------|------|
| **A. 达标型** | 固定的绝对阈值（`t_min`/`full_time`/满分层数） | 题面直接列出满分时间、满分层数 | **达到阈值 + 留 20%~50% 余量**应对评测机差异，然后**立即收手**去别的题（边际收益递减） |
| **B. 相对最优型** | **所有选手中提交的最优解** | 题面不给绝对满分线，只给"按比例插值" | **没有"够了"的概念**：先保正确性，再持续逼近物理上限（roofline）；但要评估"多花的时间 vs 可能提升的名次" |

**判断方法**：读 `evaluate.py` 的评分函数 ——
满分线是**源码常量** → A 类；满分基准来自**榜单/数据库/运行时动态统计** → B 类。
前两年（2024/2025）都是"常量阈值为主"，**今年（2nd）明确两种都有**，所以判断这一步不能省。

**B 类题的额外注意**

1. **不要为了最后几个百分点冒正确性风险**：按比例给分意味着"接近最优"也能拿大部分分，
   而一次 Wrong Answer 直接 0 分（还可能触发重测）。
2. **先算物理上限再决定投入**：用 roofline（算力上限、内存带宽上限）估算"理论上还能快几倍"。
   若已到带宽墙（实测带宽 ≈ 理论带宽的 70%+），就该停止微调。
3. **记录可复现的数字**：B 类题的性能对比会被反复引用，每次实验都要有基线、同口径、多次测量。
4. **关注"别人可能怎么做"**：B 类题的最优解往往是"算法级改进 + 充分并行 + SIMD"三件套，
   如果自己只做了常数优化，要意识到差距可能在数量级。

**A 类题的额外注意**

1. **先拿到达标分，再考虑优化**：达标即满分，多出来的性能**不额外加分**。
2. **余量比极限更重要**：同代码在不同机器上实测可差 2~3 倍，至少留 20% 余量再收手。

> **实务建议**：开赛第一件事是把所有题的 `evaluate.py` 读一遍，给每题标注 A/B 类型，再按"高确定性得分优先"排序投入时间（检测方法见 `06` §3.3）。

## 6. 仍需关注

1. **官方公告可能更新**：开始比赛工作前查看 README 的最近更新日期及 OJ 新通知；用户当前确认 Agent 辅助答题没有额外限制。
2. **2026（2nd）的题量、提交物清单、writeup 要求**：以今年 README 和各题题面为准；当前规则说明赛后 48 小时内统一提交
   一份涵盖所有得分非零题目的整体 writeup，获奖者必须提交。
   2024/2025 曾要求每题提交 `writeup.md`，不能把那两年的提交形式或计分方式套用到今年。
