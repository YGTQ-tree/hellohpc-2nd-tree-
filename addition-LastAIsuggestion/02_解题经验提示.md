# 解题经验提示（通用方法论 · 技术参考手册）

> **为什么这份文档是"通用"的**：题干、算例、甚至题型都可能与你手上的素材差别很大。
> 所以这里不复述任何一道题的答案，而是把"题目"拆成 **题型判定 → 技巧卡 → 验证流程 → 分数策略** 四件事，
> 每一部分都能直接迁移到一道没见过的新题上。
>
> **分工**：本文是**技术参考手册**（"该用哪一招"）。
> 主入口与执行流程在 `06_作答总指南.md`；规则红线在 `05_比赛规则与红线.md`；
> 集群环境事实在 `04_环境交接与工作区状态.md`；基础知识地图在 `01_知识栈与学习路线.md`。
> 两年比赛的 15 道题只作为**样本锚点**出现在 §10 的迁移表里，它们**已无法提交**，
> 但仓库里的实现与 `writeup.md` 仍是最好的素材。所有结论以各题 `evaluate.py` 的实际实现为准。

## 0. 三种使用场景

- **拿到一道全新题**：§1 建立直觉 → §2 解剖题面（填表）→ §3 定性分类 → §4 按分类挑技巧卡 → §6/§7 测量与验证 → §9 排优先级。
- **要理解/复用历史题**：看 §10 的迁移表（原型 → 技巧组合）→ 再回去读对应 `writeup.md`。
- **写完代码要交**：§7 正确性工程 → §8 评测脚本考古 → §12 一页纸检查清单（交付标准见 `06` §7）。

**一句话总纲**：性能题 = **找准瓶颈类型** × **选对技巧** × **守住正确性** × **按分数函数的形状分配时间**。
四者缺一，做出来的东西要么不快、要么不算分、要么性价比极低。

## 1. 第一性原理：任何性能题都只是在回答这 5 个问题

拿到题目先别写代码，先把下面 5 个问题答一遍（答不上来就说明还没读懂题）：

| # | 问题 | 具体要算什么 | 决定了什么 |
|---|------|-------------|-----------|
| ① | **计算量从哪来** | 主导项的数量级（n、n²、n log n、n×m、迭代次数 T） | 能不能靠"换算法"降维打击 |
| ② | **数据从哪来** | 每单位计算要搬多少字节；顺序还是随机；是否放得下 cache | 是"算得慢"还是"等内存" |
| ③ | **并行度有多大** | 最内层依赖链多长；可并行的独立维度有多宽；串行部分占比 | 上限（Amdahl）、该 SIMD 还是该多线程/多进程 |
| ④ | **机器上限是多少** | 核数 × 主频 × 每周期浮点操作数；内存带宽；网络带宽/延迟 | "理论上最快能到多少"，避免做无用的努力 |
| ⑤ | **怎么算对** | 精确整数？容差多少？守恒量？参考文件？隐藏算例？ | 哪些优化**绝对不能做**（重排、近似、投机） |

> **经验法则**：①②③ 决定量级（10× 以上），微架构技巧（§4.2/§4.3）通常只给 2–5×，除非你发现的是"算法级浪费"。
> 新题到手，先在 ① 上花 10 分钟，往往比在 ④ 上花 2 小时更值。

## 2. 题面解剖清单：拿到新题 10 分钟内必须填完的表

不要通读全文再动手，按这张表**定向检索** `readme.md` + `evaluate.py`：

| 项 | 从哪里找 | 为什么重要 |
|----|---------|-----------|
| 评测入口与**确切命令** | `evaluate.py` 里的 `subprocess.run([...])` | 命令行参数、工作目录、环境变量一个都不能猜 |
| **允许修改/提交的文件** | `readme.md` + `submit.yaml` | 改错文件 = 白干（评测会替换其他文件） |
| 输入**规模与数据分布** | 题面样例 + 生成代码 | 决定算法与索引类型；**隐藏算例可能换分布** |
| **正确性判据** | 精确相等 / MAE / 绝对误差 / 守恒量 / 哈希 | 决定误差预算，是"能不能重排浮点"的唯一依据 |
| **超时与资源** | `timeout=`、`--time`、核数/内存限制 | 决定并行度上限与"能否用大内存换时间" |
| **分数公式** | `evaluate.py` 的打分函数 | 决定边际收益（§9），以及"达标型还是相对最优型"（06 §3.3） |
| **测量协议** | warmup 次数、重复次数、取平均/最小/调和平均 | 自己实验时必须用同一套协议，否则数字不可比 |
| **计时区间** | 计时器加在哪几行 | 初始化/编译/I/O 算不算分；也关系到规则 4（不得把计算挪出计时段） |
| **算例是否固定** | 硬编码答案还是运行时生成 | 固定算例 → 可本地复现；运行时生成 → 必须通用（也禁止打表） |
| **不可修改的文件** | 题面显式声明 | 破坏接口 = 编译失败 |
| **是否可本地复现** | 有没有 MPI/Slurm/特定编译器依赖 | 决定你在哪里开发（见 §9 风险） |
| **前置关卡** | 正确性测试是否作为计分门槛 | 有的题"正确性不过 = 全部 0" |

**从分数公式反推策略**（经常被忽略，但收益极高）：

| 公式形状 | 典型写法 | 策略含义 |
|---------|---------|---------|
| 线性插值 | `(t_zero - t)/(t_zero - t_full)` | 每省一点时间都有分，值得持续迭代 |
| 对数插值 | `ln t` 归一化 | 越接近满分越难，**边际收益递减**，达到"良好"即可收手 |
| 反比型 | `full*(base-t)/(t*(base-full))` | 时间越小分数涨得越快，冲到第一档收益巨大 |
| 阶梯/档位 | 离散层数、达标线 | 跨越一档 = 固定收益，值得为"下一档"专门优化 |
| 达标制 | 跑通给 50 分 | **先把它拿到手**，再谈性能 |
| 相对排名 | 与其它参赛者插值 | 关注"有没有明显短板"，木桶效应 |

## 3. 题型分类决策树（先定性，再动手）

任何一道性能题，先归到下面 5 个原型之一（可以是组合）。**分类错了，后面全错。**
（`06` §4 另有一张"题型皮 → 主攻方向"的速查表，含图计算/网络 IO/AI 量化等近年常见皮。
**注意两套编号不是一回事**：本节 A–E 是**瓶颈分类**，`06` §4 的 A–J 是**题型皮编号**，不要混用。）

```
题目 → 先看是不是"环境/工程"题（要求你编译、配置、提交脚本、调参）
        ├─ 是 → 【E 工程配置型】：杠杆在"选库/选编译器/写对配置文件/参数搜索"
        └─ 否 → 看计算量随规模的增长（做 2~3 个规模的小实验，画 log-log 斜率）
                 ├─ 斜率明显 > 1（如 n²） → 【A 算法降复杂度型】：杠杆在换算法
                 └─ 斜率 ≈ 1 → 看单位计算的访存量
                        ├─ 访存 >> 计算（每字节只算 1~2 次） → 【C 访存带宽型】：杠杆在数据布局/压缩/减少遍历遍数
                        └─ 计算 >> 访存 → 【B 计算吞吐型】：杠杆在 SIMD/ILP/多核
        ※ 只要涉及多进程/多节点 → 叠加 【D 并行通信型】：杠杆在分解方式与通信量
```

| 原型 | 判定信号 | 第一招 | 常见上限 | 典型翻车原因 |
|------|---------|--------|---------|-------------|
| **A 算法降复杂度** | n 一大就爆炸；暴力枚举明显 | 找重复计算/对称性/数学恒等式；把"求解"变成"排序/扫描" | O(n²)→O(n log n) 是 10²~10⁵ 倍 | 只看小算例，没意识到真实规模 |
| **B 计算吞吐** | 时间与运算次数成正比；cache 命中好 | SIMD + 多核 + 拆依赖链 | 核数×向量宽度（几十倍） | 依赖链没拆，SIMD 空转；浮点重排把正确性做没了 |
| **C 访存带宽** | cache-miss 高、IPC 低；加计算不涨时间 | 减少遍历遍数、位压缩/打包、分块提高复用、换布局 | 内存带宽/数据量（几倍） | 一直在抠算术，没意识到带宽已打满 |
| **D 并行通信** | 多进程加速比不线性；计时显示等待 | 减少通信次数、聚合消息、计算通信重叠、改分解 | 通信量/带宽 + 延迟 | 通信粒度太细、同步点太多、负载不均 |
| **E 工程配置** | 要求"编译/提交/调参"而非写算法 | 先把流程跑通，再换最快的库、再扫参数 | 库与参数带来的 2–5 倍 | 配置文件写错；超时；只允许一组参数却交多组 |

> **混合题型**：例如"O(N²) 计算 + 多核并行" = A（对称性减半）+ B（SIMD）+ D（并行）；
> "大规模排序" = A（换成线性排序）+ C（带宽）+ B（多核）。**每识别出一个原型，就去 §4 取对应的技巧卡。**

## 4. 通用技巧卡（核心章节）

每张卡：**适用信号 / 原理 / 做法 / 风险 / 验证**。带 ★ 的是"最高杠杆、最常考"。

### 4.1 算法层（改的是"要算多少"）

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T1 ★** | **换算法降复杂度** | 规模一大就爆炸；存在重复子问题 | ① 找出被重复计算的部分（两两交互、重复求和、重复查找）② 用排序/哈希/前缀和/分治把它变成一次线性扫描 ③ 用数学恒等式化简求和式 | 新算法常数可能更大（小算例反而慢）；数值行为改变 | 两个规模点上对比时间增长曲线；与暴力实现对拍小规模 |
| **T2 ★** | **对称性 / 去重 / 剪枝** | 两两交互、矩阵对称、成对量、大量无效组合 | 只算一半再反向写入；按排序/分桶跳过不可能的组合；early-exit | **并行写冲突**（要原子或分块）；**浮点累加顺序改变** | 与串行版对拍 + 检查误差量级是否在容差内 |
| **T3 ★** | **贪心 + 交换论证** | "最小化最大值/最优排列/最优顺序/资源分配" | 考虑相邻两个元素交换，把"哪种顺序更优"化成可比较的量 → 得到**排序键**；乘法型取对数即变加法型 | 排序键推错（方向反了/键不完整）；平局是否影响答案 | **暴力枚举小规模全排列**对拍（几行 Python 就能做，务必做） |
| **T4 ★** | **排序即原语** | 需要分组/去重/求前缀极值/按序扫描 | ① 把待排数据**编码成单个整数键**（多字段打包，见 T8）② 键位宽有限 → 计数/基数/桶排序（O(n)）③ 并行时"局部直方图 + 全局前缀和 + 分散写回" | 基数排序要双缓冲（内存×2）；稳定性；键位宽算错会溢出 | 与 `std::sort` 对拍；检查**溢出**与极端键值 |
| **T5 ★** | **前缀和 / 差分 / 一次扫描** | 反复求"前 i 项的和/最大值"；区间查询 | 预处理一次 O(n) 扫描回答所有查询；并行用两级 scan（块内 + 块间） | 整数溢出（先估上界）；并行 scan 的边界 off-by-one | 与朴素 O(n²) 对拍；构造极端数据（全同、递增、全负） |
| **T6** | **预计算 / 查表 / 位运算代替算术** | 小值域函数被反复调用；大量分支的分类；布尔集合运算 | 打表（值域小）、位图、popcount/clz/ctz、位并行技巧 | 表太大致 cache 失效；可读性差 | 边界值逐一遍历；确认 cache 没变差 |
| **T7** | **分治 / 分块 / 倍增** | 规模大但可递归拆；重复区间查询 | 递归拆分 + 合并；倍增预处理（log 级查询）；把大问题切成 cache 友好的块 | 递归开销、并行度反而下降 | 与朴素版对拍；测不同块大小 |
| **T8 ★** | **数据压缩 / 打包** | 元素很小（bool/小整数）；访存瓶颈；内存吃紧 | 多字段塞进一个字（位域/移位）；布尔用位图；用最小够用的类型 | 解包开销；**位宽算错就全错** | 打包/解包往返测试；边界值（最大值恰好占满位宽） |

### 4.2 单核微架构层（改的是"每条指令的效率"）

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T9 ★** | **强度削弱 / 消除昂贵运算** | 热循环里有 `sqrt`/除法/`pow`/`exp`/取模 | ① 比较 `sqrt(a)<b` → 比较 `a<b*b` ② `x/sqrt(x)` 形式改用 `r²` 与 `1/r³` 组织 ③ 除法 → 乘倒数 ④ 多项式用 **Horner** ⑤ 循环不变量外提、公共子表达式合并 | 数值范围/溢出（`b*b` 溢出）；倒数精度 | 与原始公式对拍；测边界（0、极大、极小、负） |
| **T10 ★** | **拆依赖链（加 ILP）** | IPC 低但 cache 正常；迭代时间 ≈ 单条链延迟×次数 | 开 2/4/8 个独立累加器最后合并；手动展开；把可并行的子计算挪到链外 | **浮点结果改变**（只能在容差允许时用） | 对比容差；看 IPC 是否上升 |
| **T11 ★** | **循环交换 / 分块（tiling）** | 跨步访问、数组远超 cache、miss 率高 | 交换内外层让最内层连续；按块处理让工作集进 L1/L2（strip mining） | 交换后依赖关系变化；并行化后被拆得过碎 | 测多组块大小；看 L1/L2 miss |
| **T12 ★** | **内存布局变换** | 结构体数组（AoS）但只用其中几个字段；跨步访问 | **AoS→SoA**（每字段独立数组）；热/冷字段拆分；对齐（64B）；线程私有变量加 padding 防伪共享 | 转换本身要遍历一遍；接口变化大；**别改不可修改的文件** | 计时 + 检查转换开销是否被计入计时区间 |
| **T13** | **分支消除 / 可预测化** | 热循环里有数据相关的 if；分支失败率高 | 把 if 提到循环外/拆成两段循环；无分支写法（掩码、条件传送）；预排序让分支规律 | 可读性；有时"提前 return"更快 | 两种写法对比；看 branch-misses |
| **T14 ★** | **给编译器递信息** | 编译器"不敢"优化（别名、对齐、次数未知） | `restrict`/`const`、`__builtin_assume_aligned`、`#pragma omp simd`、`#pragma clang loop vectorize(enable) unroll(4)`、把 `-Rpass*` 的抱怨逐条消掉 | 断言错了就是 UB | `-Rpass=vectorize` / `objdump -d` 确认真的生成了向量指令 |

### 4.3 向量化层（SIMD）

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T15 ★** | **让编译器自动向量化** | 内层是连续、独立、无分支的算术 | 消除下面的 8 大失败原因 | 自动向量化会引入 FMA/重排 → 数值变化 | `-Rpass=vectorize` 确认成功；`-Rpass-missed=vectorize` 看原因 |
| **T16 ★** | **手写 SIMD intrinsic** | 自动向量化做不到，或需要精确控制 | 用平台头文件（如 `arm_neon.h`）与可移植包装；**用 `#if defined(__aarch64__)` 包住并提供标量 fallback**（否则本地 x86 无法验证）；处理尾块 | FMA 与手写重排改变浮点结果；平台不兼容 | 与标量版对拍（容差内）；`objdump` 确认指令 |
| **T17 ★** | **选对"放进 lane 的维度"** | 想向量化却找不到并行维度 | ① 优先最内层连续维度 ② 若内层有依赖，把**外层独立任务**放进 lane（循环交换/转置/多任务打包）③ 粒度不足时把同一个体的多个独立量打包 | 索引写错；尾部浪费（如 4 宽只用 2） | 逐步增加宽度对比；正确性回归 |

> **向量化失败的 8 大原因速查**（对应 T15/T16/T17）：
> ① 跨迭代依赖 ② 指针可能别名 ③ 循环内有分支/`break` ④ 非连续/变步长访问
> ⑤ 循环次数未知或非常量 ⑥ 函数调用未内联 ⑦ 归约形式编译器不认识 ⑧ 数据类型不匹配（如 int 与 float 混算）。
> 补充：`sqrt`/`log`/`atan2` 等 libm 调用**默认不会自动向量化**（本集群 ARM 的 glibc 没有 libmvec）。

### 4.4 共享内存并行层（多线程）

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T18 ★** | **把问题映射到并行原语** | 任何要并行的题 | 先归类：**map**（逐元素）／**reduction**（求和求最值）／**scan**（前缀）／**histogram**（分桶计数）／**sort**／**stencil**（邻域更新）／**任务池**（不规则）→ 套成熟模式，别自创 | 归约的浮点顺序不定；histogram 写冲突 | 串行版对拍；不同线程数下结果一致性 |
| **T19 ★** | **调度与负载均衡** | 各迭代工作量差异大；加速比不线性 | `static`（均匀）/`dynamic`/`guided`（不均）；调整 chunk 与粒度；`collapse(2)` 合并循环 | 粒度过细 → 调度开销；过粗 → 长尾 | 测不同调度/线程数，看**最后一个线程何时结束** |
| **T20 ★** | **亲和性 / 伪共享 / NUMA** | 线程数上去了反而慢；多路机器 | 绑核（`OMP_PROC_BIND`/`OMP_PLACES` 或 `sched_setaffinity`）；线程私有数据 padding 到 cache line；**并行 first-touch** 初始化；必要时 `numactl --interleave` | 绑核不当会互相抢核 | 多线程扩展曲线；cache 行弹跳迹象 |
| **T21** | **控制并行开销** | 循环太短、并行区反复进出、锁太多 | 并行区尽量往外提（粗粒度）；热路径避免加锁（局部累加 + 最后合并）；**注意计时区间是否包含线程创建/初始化** | 并行区外提会改变内存语义 | 单线程 vs 多线程的小算例时间（暴露固定开销） |

> **同步原语在 128 核上会成为真瓶颈**（实测三代屏障：串行轮询 437 µs → 全核自旋同一条 cache line 1913 µs →
> 分组完成计数器 + `wfe/sev` 4.31 µs）。核数超过 32 之后，先把同步与访存算清楚（详见 `06` §5.5）。

### 4.5 分布式层（多进程 / MPI）

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T22 ★** | **域分解与冗余计算权衡** | 多进程需要彼此的数据 | 按数据/按任务分解；邻域依赖用 halo 交换；数据量不大时**直接全员广播/Allgather** 比点对点更简单可靠；宁可冗余算也不要频繁通信 | 分解不均 → 长尾；通信量随进程数增长 | 强扩展/弱扩展曲线 |
| **T23 ★** | **通信量最小化与聚合** | 消息又多又小 | 记住 `t ≈ α + β·n`：**减少消息条数**比减少字节数更重要；能合并就合并成一次大消息；减少全局同步点 | 聚合需要额外缓冲与内存 | 计时对比（通信占比）；`-n 2/4/8` 小规模扫 |
| **T24** | **通信与计算重叠** | 通信等待明显 | 非阻塞 `Isend/Irecv` + 计算；双缓冲；流水线化 | 缓冲区生命周期出错；复杂度上升 | 与阻塞版对比；确认结果一致 |
| **T25 ★** | **集合通信选型** | 需要广播/汇总/分发 | `Bcast`（一对多同一份）／`Scatter`（一对多分发不同块）／`Gather`（多对一）／`Allgather`（人人有全量）／`Reduce`（多对一归约）／`Allreduce`（人人要结果，更贵）／`Scan`（前缀）。**只在需要时用更贵的那个** | 语义用错；**所有进程必须都调用集合操作**，放错分支会挂死 | 小进程数跑通 + 打印校验 |

> **先算规模再选架构**：问题小到能整块放进单机内存时（几百万边 / 几十 MB），共享内存往往**完胜** MPI
> （实测某图题：官方 MPI+AML 参考实现单进程 4e7 TEPS，整图放共享内存后高一个数量级）。

### 4.6 系统 / 工程层

| 卡 | 技巧 | 适用信号 | 做法要点 | 风险 | 验证 |
|----|------|---------|---------|------|------|
| **T26 ★** | **换库 / 换实现（最高杠杆之一）** | 题目用的是标准/朴素实现；存在成熟高性能库 | 换 BLAS/LAPACK/FFT/稀疏/排序库；注意 **ABI 与线程模型**（库自带线程时别和 OpenMP 超订，如 `OPENBLAS_NUM_THREADS=1`） | 链接错误、版本冲突、结果差异 | 先跑通再对比性能；记录用了哪个 module/库 |
| **T27 ★** | **编译选项与构建方式** | 有权限改编译配置 | `-O3`、`-march/-mcpu`、LTO、PGO、`-funroll-loops`、`-fno-math-errno`、`-ffp-contract`；**评测可能固定编译选项**，那就从源码层（pragma/attribute/intrinsic）下手 | 某些选项破坏正确性（`-ffast-math`、`-march=native`）；平台不匹配 | 每次只改一个选项，记录时间与正确性 |
| **T28 ★** | **参数搜索** | 有可调参数（分块、规模、进程网格、粒度） | 先粗扫定位量级，再细扫；利用单调性做二分；注意**预算与约束**（有时只允许一组参数、有超时） | 参数间交互（非单峰）；把评测时间用完导致超时 | 记录参数-性能表；找稳健区间而非尖峰 |
| **T29** | **I/O 与启动开销** | 计时区间包含读文件/初始化/首次调用 | 并行 I/O；减少重复初始化；预热（warmup）；避免首次触碰大内存的缺页抖动 | 把初始化优化掉但评测其实不计时 → 白费 | 用计时打点拆出各阶段时间 |
| **T30 ★** | **误差预算与"可重排性"判定** | 浮点 + 容差判据 | 先量化：**允许偏差 / 答案量级 = 相对容差**。整数/精确语义 → 随便重排；浮点 → 只有相对容差 ≫ 单次舍入（≈1e-16×量级×√n）时才敢重排；**迭代/混沌系统误差指数放大，必须保持运算顺序** | 低估放大效应 → 小算例过、大算例挂 | 用**全部**给定算例 + 多随机种子做回归 |
| **T31** | **等价变形（保序/整数化）** | 需要在"不变结果"前提下提速 | 保序变换（同乘正数、加常数）、整数化（定点/有理数）、用更高精度换取重排自由（Kahan 补偿求和、double 替 float） | 整数溢出；精度提升带来的减速 | 逐位/逐项对拍；边界数据 |
| **T32** | **精度换速度（谨慎）** | 容差宽松、瓶颈在精度上 | `float` 替 `double`、近似函数、`-ffast-math`、查表近似 | 误差超限是最常见的 0 分原因之一 | 全算例误差统计（平均值 + **最大值**，别只看平均） |

## 5. 技巧 → 验证方法 总表

任何优化都必须回答"我怎么知道它是对的"。通用验证手段只有六种，按可信度排序：

| 手段 | 做法 | 适用 | 强度 |
|------|------|------|------|
| **保留串行参考** | 串行版/朴素版留着，逐元素对拍 | 一切题目 | ★★★★★ |
| **暴力枚举 / 小规模全解** | 小 n 时枚举所有可能（排列、路径、状态）与你的解对比 | 有贪心/启发式的题（T3） | ★★★★★ |
| **不变量 / 守恒量** | 质量、能量、动量、总量、和、计数、哈希 | 模拟类、迭代类 | ★★★★ |
| **黄金数据对拍** | 与题目给的参考输出对比（注意判据是精确还是容差） | 有 `ref*` 文件的题 | ★★★★ |
| **性质测试 / 随机化** | 随机生成大量合法输入，检查输出满足性质（有序、和为定值等） | 数据生成自由的题 | ★★★ |
| **微基准（microbenchmark）** | 单独抽出热点函数，用不同实现跑同一份数据 | 性能对比 | ★★★（只证性能） |

**边界测试清单（每题都过一遍）**：n=0/1/2；非整倍数（n 不整除进程数/向量宽度）；非对齐偏移；负数/零/极大极小；重复元素；全部相同；退化输入（全 0、空区间）；恰好溢出边界；浮点特殊值（NaN/Inf/次正规）。

## 6. 性能测量方法论

1. **先建可信 baseline**：与评测完全相同的命令、相同的计时区间、相同的环境变量。第一遍只用来热身。
2. **统计量选择**：多跑几次，报告 **min 或中位数**；评测用平均/调和平均时，你自己也要用同一口径。
   **本集群实测同算例重复测可有 ±40% 抖动 → 任何性能结论必须 ≥3 次取中位数。**
3. **量化上限（最重要的习惯）**
   - 计算上限：`核数 × 主频 × 每周期浮点操作数`；对比实测 GFLOPS，算出"利用率"。
   - 访存上限：`数据量 / 带宽`；若实测已接近它，**说明撞到带宽墙，别再抠算术**。
   - 并行上限：Amdahl —— 串行占比 5% 时最多也就 20×。
   - 结论要么是"还有 10× 空间，继续"，要么是"只剩 1.2×，收手去别的题"。
4. **定位瓶颈**
   - **本集群没有 `perf`**（登录节点与计算节点都没有；登录节点 `/proc/sys/kernel/perf_event_paranoid` 也不允许）。
     替代手法：**数调用次数 × 单次成本**、分段计时（把大循环拆段分别计时）、二分注释（注释掉一半代码看时间怎么变）、
     缩小规模看趋势、`gprof`/`gdb`/`strace`。
   - 若有 `perf`（例如本地机器），指标判读表：

   | 现象 | 结论 | 去看哪张卡 |
   |------|------|-----------|
   | IPC 低、cache-miss 高 | 访存瓶颈 | T11 T12 T8 T4 |
   | IPC 低、miss 低、分支失败高 | 分支/依赖链 | T13 T10 |
   | IPC 高、指令数巨大 | 算法常数问题 | T1 T9 |
   | 单核很快、多核不涨 | 并行度/负载/伪共享/带宽 | T19 T20 T21 |
   | 多进程不涨 | 通信/同步 | T23 T24 T25 |

5. **测量陷阱**：频率漂移与温控；机器上还有别人的作业；cache 冷热；**编译器把要测的代码优化没了**
   （把结果写出去 / 加 `volatile` / 用 `asm volatile("" ::: "memory")`）；计时区间与评测不一致；只跑一次就下结论；
   **忘了重新编译，跑的是旧二进制**。

## 7. 正确性工程（三条防线）

| 防线 | 做什么 | 成本 |
|------|--------|------|
| **第一层：小规模对拍** | 保留朴素实现，写脚本对小规模随机数据自动对比；**在写优化版之前就把脚本写好** | 低，收益最高 |
| **第二层：不变量与守恒量** | 模拟类检查守恒量；排序类检查有序性与元素集合；组合类检查性质 | 低 |
| **第三层：泛化压力测试** | 用**多个随机种子/多种数据分布/全部给定算例**跑回归；构造极端数据 | 中，但能抓住"过拟合到样例"的错 |

> 交付时还要做 `06` §7.3 的**三层验证法**：未改源码留底 → 与自身版本逐位对比 → 与官方参考对比。

**浮点重排决策流程**（几乎所有数值题的生死线）：

```
我要改变浮点运算顺序（并行归约/向量化/对称化/分块）
 ├─ 结果判据是精确相等？ ── 是 → 禁止重排
 └─ 否 → 算相对容差 = 允许偏差 / 答案量级
          ├─ 相对容差 ≫ 1e-12（宽松） → 可以重排，但仍要全算例回归
          └─ 相对容差 ≲ 1e-12（严苛） → 不要重排数值核心；
                                        只并行"互不影响"的维度（如按个体并行，保持每个个体内部顺序）；
                                        或先提高精度（double/补偿求和）再考虑
 ※ 迭代/混沌/长时间积分系统：误差随时间指数放大 → 任何重排都要按"最坏算例"实测，不能只推公式
 ※ 需要与参考实现比对时，编译必须显式 -ffp-contract=off（gcc 默认会合 FMA）
```

**反打表原则**：算法必须对**任意合法输入**成立。不要把样例答案写进代码、不要依赖特定随机数种子或数据分布、不要假设 n 恰好是某个值或恰好整除。评测方通常都会"适当修改示例算例中的数据"。

## 8. 评测脚本考古学（10 分钟看懂一个评测系统）

从 `evaluate.py`（或任何评测入口）里**必须**抄下来这些：

1. 编译命令与工作目录（含 `cwd=`）、环境变量要求、**编译超时**。
2. 运行命令、参数、`timeout`、绑核方式（`taskset`/`numactl`/`srun`）。
3. 计时取自哪里（程序 stdout？外部计时？）——决定你能不能改输出格式（通常**不能**）。
4. 正确性判定函数（精确/容差/哈希/守恒量）。
5. 分数函数与阈值表、各算例权重，以及**满分线是常量还是动态取榜单**（→ 达标型/相对最优型）。
6. warmup 与重复次数、统计量。
7. 资源校验（有的脚本会检查核数/OMP 环境变量，不满足直接退出）。
8. 它对文件做了哪些**破坏性操作**（覆盖、删除、改写）→ 跑前备份。
9. 前置门槛（正确性测试不过就全 0；数据下载失败就无法评测）。
10. 提交物清单与路径（`submit.yaml`）。

**本地模拟评测的正确姿势**：不要修改仓库里的 `evaluate.py`（评测方用自己那份，改了也没用，还可能被判定为异常行为）。做法是：
- 能跑就跑原脚本；
- 环境不满足（核数不足/缺 MPI/Slurm）时，**另存一份副本**改资源校验，或者直接手动运行二进制并手算分数；
- 把"手动版评测流程"写成一条命令，保证每次改动后一键回归。

## 9. 时间与风险管理（比赛节奏）

**性价比公式**：`优先级 = (预期得分增益 × 达成概率) / 预计耗时`。每题等权时，先把"高概率、低耗时"的分拿走。

| 阶段 | 时间占比 | 目标 |
|------|---------|------|
| 侦察 | 10% | 全部读完题面 + 评测脚本，填完 §2 的表，给每题标注达标型/相对最优型，排出优先级 |
| 保底 | 20% | 每题的"送分段"：跑通/正确性/小算例/达标制的那部分 |
| 主攻 | 50% | 选 1–2 题做到高分（按性价比排序），其余保持保底 |
| 收尾 | 20% | 回归测试、writeup、打包提交、留缓冲 |

**风险清单**

- **不可复现的优化**：改完不记录 → 回不去了。每次有效改动都 `git commit` 或另存文件。
- **过度优化一道题**：边际收益递减（对数型/接近满分时），及时切换到别的题。
- **环境依赖**：本地过 ≠ 集群过（架构、编译器、核数、FMA、数学库都不同）→ 预留集群复测时间。
- **数据依赖**：`download.sh` 指向的路径可能整棵树都没了 → 开工前先确认（06 §3.4）。
- **不可逆操作**：评测脚本可能删目录/改文件 → 动手前备份。
- **单点阻塞**：某个工具/库装不上，别死磕，换等价路线（换库、换算法、换实现方式）。
- **评测机排队**：QOS 常限制同时只能有 1 个作业 → 提前规划集群时间，别把测量挤到最后。
- **最后 10 分钟不要做大改动**：只做提交动作。

## 10. 迁移表：把题型抽象成技巧组合（换个包装就是新题）

| **O(N²) 两两交互 + 多进程**（素材：N_Body） | **A + B + D 复合** | T2（对称性，有风险）、T9（去 sqrt/除法）、T11/T12（分块与布局）、T18/T19（并行归约）、T22/T25（Bcast/Allgather/Reduce）、**T30（误差预算，命门）** | 粒子模拟/分子动力学/SPH、Ising/元胞自动机、卷积/Stencil —— 套路都是"**两两或邻域交互 O(N²) → 用对称与分块降到可接受，再把力/场的累加按安全方式并行**" |
| **长步数时间积分仿真**（素材：2025 的两道仿真题） | **H 仿真型 + B 吞吐型** | T9（常量表外提）、T12（扁平数组/双缓冲）、T27（Debug→Release）、T18/T19/T20（空间并行 + 线程池）、T30 | 气象/流体/分子动力学 —— 套路都是"**先摘零数值风险的固定开销，再按空间维并行（保持每个元素内部运算顺序）**" |
| **不规则访存图计算**（素材：2025 graph500） | **G 图计算型** | T4/T5（重排与前缀）、T8（位图 frontier）、T19/T20（负载均衡与伪共享）、T21（同步开销）、T7 | BFS/SSSP/PageRank/连通分量 —— 套路都是"**direction-optimizing + 位图 frontier + 按度数重排；核多了先把屏障/原子冲突算清楚**" |
| **协议/解析密集 IO**（素材：2025 m4c） | **F IO 型** | T29（批量与流水线）、T23（减少往返次数）、T21（连接复用） | HTTP/RPC 客户端、日志解析、格式转换 —— 套路都是"**先量清对端吞吐，再谈优化；批量 + 复用连接是吞吐关键**" |
| **量化/算子级 kernel**（素材：2025 amazing_llm） | **I 数值 kernel 型** | T12（布局与带宽）、T16（向量化）、T26（换库/扩展）、T32（精度换速度） | 反量化/量化、算子融合、自定义 C++ 扩展 —— 套路都是"**访存带宽为王；先证明与 baseline 逐位一致，再谈速度**" |

**从这张表能提炼的三条通用教训**

1. **绝大多数"看起来不同的题"只有几种骨架**：线性扫描类、两两交互类、独立迭代类、排序/扫描类、图/组合搜索类、仿真类、IO 类、工程配置类。识别骨架 → 套对应技巧，比逐题记忆有效得多。
2. **能改算法就不要先改常数**：T1/T3/T4/T5 的收益通常是 10²~10⁵，微架构技巧是 2~5×。
   （工程实践上仍建议先做零风险的编译选项/固定开销优化，见 `06` §4 的说明。）
3. **数值-并行的耦合是所有科学计算题的共同难点**：题目越"物理"，答案越依赖运算顺序；
   此时**并行化"互不影响的维度"**（而不是重排求和）往往是最优解。

## 11. 通用代码骨架

**并行归约（安全的浮点写法：局部累加 + 最后合并）**
```c
double local[64] = {0};              // 每线程一个槽位，避免伪共享（若用 OpenMP）
#pragma omp parallel
{
    int t = omp_get_thread_num();
    double acc = 0;                  // 线程私有累加器（保持串行顺序）
    #pragma omp for schedule(static) nowait
    for (long i = 0; i < n; i++) acc += f(i);
    local[t] = acc;
}
double total = 0; for (int t = 0; t < nth; t++) total += local[t];   // 顺序合并
```

**并行前缀和（两级 scan）**
```c
// 1) 分块求和  2) 块间前缀和（小数组，串行也够快）  3) 块内重扫累加偏移
for (b = 0; b < nb; b++) blk[b] = sum(block b);
excl = exclusive_scan(blk);
#pragma omp parallel for schedule(static)
for (b = 0; b < nb; b++) { long long run = excl[b];
    for (i = lo[b]; i < hi[b]; i++) { run += a[i]; out[i] = run; } }
```

**向量化前的自查（对应 T14/T15）**
```c
void kern(const float * restrict x, float * restrict y, long n) {
    #pragma omp simd
    for (long i = 0; i < n; i++) y[i] = a*x[i]*x[i] + b*x[i] + c;   // 无分支/无别名/连续
}
// 验证：clang -O3 -Rpass=vectorize -Rpass-missed=vectorize -S kern.c
```

**基数排序骨架（LSD，键为无符号整数）**
```c
for (pass = 0; pass < npass; pass++) {          // 每 pass 处理 BITS 位
    memset(cnt, 0, sizeof cnt);                  // 每线程局部直方图 -> 全局前缀和
    for (i = 0; i < n; i++) cnt[(key[i] >> shift) & MASK]++;
    /* 前缀和 -> 每线程每桶的起始偏移 */
    for (i = 0; i < n; i++) tmp[pos[(key[i] >> shift) & MASK]++] = key[i];
    swap(key, tmp);                              // 双缓冲
}
```

**MPI 集合通信骨架（对应 T22/T25）**
```c
MPI_Bcast(buf, n, MPI_DOUBLE, 0, MPI_COMM_WORLD);                                // 一对多，同一份
MPI_Allgather(local, ln, MPI_DOUBLE, glob, ln, MPI_DOUBLE, MPI_COMM_WORLD);      // 人人有全量
MPI_Reduce(&local_sum, &global_sum, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);  // 多对一
/* 注意：集合操作必须被所有进程执行，通常不能放在 if(rank==0) 里面 */
```

## 12. 一页纸 Checklist（拿到新题照做）

**侦察**
- [ ] 读 `readme.md`（任务/约束/提交物/评分）与 `evaluate.py`（编译运行命令、超时、判据、分数函数、warmup、资源校验、破坏性操作）

- [ ] 确认数据是否还在（`download.sh` 的路径）；确认能否本地复现，不能则提前规划集群时间
- [ ] 判断达标型 / 相对最优型

**定性**
- [ ] 用 2~3 个规模点测时间增长 → 定原型（A/B/C/D/E）
- [ ] 算上限（计算峰值、内存带宽、Amdahl）—— 得到"最好还能快几倍"

**优化**
- [ ] 先写基线版 + 小规模对拍脚本（先于优化）
- [ ] 顺序：编译选项 → 热路径固定开销 → 内存布局 → 向量化 → 多线程 → 算法；同时确认算法层有无数量级机会
- [ ] 一次只改一个变量；每次都记录「版本-参数-时间-正确性」；用上限估算判断"还有多少空间"

**正确性**
- [ ] 小规模对拍全部通过；边界清单逐项过（n=0/1、非整除、非对齐、极值、退化）
- [ ] 浮点重排走过 §7 的决策流程；用**全部**算例 + 多随机种子回归
- [ ] 检查是否**无意中打表**（依赖特定种子/数据分布）；检查计算是否都在计时段内

**收尾**
- [ ] 按评测脚本原样复跑一次，数字以它为准（≥3 次取中位数）
- [ ] 备份、写 `writeup.md`（结构与要求见 `06` §7.2）
- [ ] 打包提交并核对 zip 清单（与 `submit.yaml` 一致）；留出缓冲时间，最后阶段不做大改动

## 附录 A：跨题通用的工程事实

- 评测脚本普遍会：替换你交的文件 → 用固定命令编译（**有超时**）→ 多轮运行取平均 → 解析 stdout → 比对答案 → 按公式给分。
  **任何一环不符合预期都是 0 分**。
- 计时段边界千差万别：有的只统计核心函数，有的统计每步若干函数之和，有的把整个进程（含读文件）都算进去。
  **必须逐题确认，并注意规则 4（不得把计算挪出计时段）。**
- 平台相关的事实：集群是 **ARM aarch64（鲲鹏 920，NEON 128 位）**为主，也有 x86 节点；
  本地 x86 能验证算法正确性，但**性能结论必须回集群复测**；**参考输出必须在目标平台上生成**。
- 行尾统一 LF；登录节点不跑高负载；不合作、不攻击、不打表、不把计算挪出计时段——
  这些规则在任何一届都不变（全文见 `05`）。
- 各历史题的具体阈值/文件名清单在其自身仓库的 `readme.md` 与 `evaluate.py` 里，需要时现查，不要背。
