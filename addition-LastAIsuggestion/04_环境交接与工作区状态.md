## 4. Slurm 提交 Cookbook（实测踩坑总结）

**四条硬规则**

1. **必须写 `-p <分区> -q <同名QOS> -A acct-stu`**。不写 `-q` → `srun: error: Unable to allocate resources: Invalid qos specification`。
2. **不要写 `--mem`**：默认按 **1950 MB/核** 配给（`-c 128` ⇒ 约 244 GB，够用）。
   写了更大的 `--mem` 会被**折算成更多 CPU** → 撞 `QOSMaxCpuPerUserLimit`（例：`-c 8 --mem=16G` 被当成 9 核）。
   反过来，**核要够多**：OOM kill 常常不打印程序的最后一行输出，判题正则匹配不到 → 直接 0 分。
3. **`srun` 起不了 OpenMPI**（`MPI_Init` 拿不到 communicator）→ **MPI 程序一律 `sbatch` + 脚本内 `mpirun -np N`**。
4. **提交前先清空自己的作业**（QOS MaxJobs=1）：`squeue -u $USER` → `scancel -u $USER`。

**模板**

```bash
#!/bin/bash
#SBATCH -J <name>
#SBATCH -p kp_run                 # 分区（先现探，见 §3）
#SBATCH -q kp_run                 # QOS，名字常与分区同名
#SBATCH -A acct-stu               # 账户，必须写
#SBATCH -N 1
#SBATCH -c 128                    # 核数；默认 1950MB/核，故不要写 --mem
#SBATCH -t 01:00:00               # kp_run 上限 2h
#SBATCH -o ~/<work>/slurm_%j.out
#SBATCH -e ~/<work>/slurm_%j.err
cd "$SLURM_SUBMIT_DIR"            # 一定要 cd：sbatch 的工作目录是提交时的 cwd
echo "HOST=$(hostname) NPROC=$(nproc)"   # 先确认拿到了几核
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK   # 用 OpenMP 时
./your_program
```

- **128 核 MPI**：`-N 1 --ntasks-per-node=128 -c 1`，脚本里 `mpirun -np 128 ./prog`。
- **8 核 OpenMP**：`-c 8`，脚本里 `export OMP_NUM_THREADS=8; ./prog`（不要用 `-n 8` 跑 OpenMP，那会起 8 个进程）。
- **编译也放进 sbatch**：登录节点不许跑重活；128 核节点上编译一个小工程只要几秒。
- `taskset -c 0` 在 srun/sbatch 分配内会报"设置亲和力失败: Invalid argument"（分配到的核未必是 0 号）→ **不要手动硬写核号**，让 `evaluate.py` 自己探测。

**交互调试**：`salloc -p kp_interact -q kp_interact -c 8 -t 2:00:00`。
注意 salloc 结束后你仍在登录节点，要 `ssh arm_cal`（或 `srun`）进计算节点；VSCode 请在**计算节点**上用。

**常用命令**：`squeue -u $USER`、`sacct -j <id> --format=Elapsed,State,AllocCPUS,MaxRSS,ReqMem`、`scancel <id>`、`scontrol show job <id>`。
`squeue` 的 CPUS 列能立刻暴露"内存超配导致核数变多"。

## 5. 编译器、工具与 Python 环境（2026-09-21 实测）

| 工具 | 登录节点 kp001 | 计算节点 kp026 | 说明 |
|------|---------------|---------------|------|
| `g++` / `gcc` | 10.3.1 | **10.3.1** | **`-fopenmp` 实测可用**（`omp.h` 存在，编译通过） |
| `clang++` | 有（clang 12），但**没有 `omp.h`** → `-fopenmp` 直接失败（据 2026-09-20 实测） | **没有**（本次实测确认） | 所以"用 clang 写 OpenMP"这条路在集群上不通 |
| `cmake` | 有 | `/usr/bin/cmake`（默认选 `/usr/bin/c++` = g++ 10.3.1） | 若题目锁定 clang，会直接编不过 |
| `perf` | ❌ 没有 | ❌ **没有** | 别浪费时间找；热点定位靠"数调用次数 × 单次成本 + 分段计时 + 缩小规模" |
| `gprof` / `gdb` / `strace` | ✅ | ✅ | 没有 perf 时的替代 |
| `valgrind` / `ltrace` | ❌ | ❌ | — |
| `taskset` `numactl` `rsync` `zip` | ✅ | ✅ | `evaluate.py` 常用 taskset/numactl |
| `python3` | **3.9.9** | — | `pyyaml 6.0.3` 可用（已装在 `~/.local`，家目录共享，计算节点也能 import） |

**推论**

- **不要赌 OpenMP 一定存在**：判题机用哪个编译器不由你决定（历史题目里就出现过 `cmake` 选 g++、题面却提 clang 的情况）。
  需要并行时的零依赖方案是 **`std::thread` 常驻线程池（约 30 行）**；线程数不要硬编码，
  按 `环境变量 > sched_getaffinity() > cgroup cpu.max > hardware_concurrency()` 的优先级取。
- 若换新账号/新机器后计算节点报 `ModuleNotFoundError: No module named 'yaml'`，
  用 `python3 -m pip install --user --force-reinstall pyyaml`（登录节点已自带，不加 `--force-reinstall` 会被"已存在"跳过）。

## 7. 同步工作副本的坑

`rsync` 会把本地的 `*.o`、`build/`、`.buildmode`、可执行文件一起同步过去，导致集群上 `make` 输出
`make: 对"all"无需做任何事。`——**你以为编译了，其实用的是 x86 的旧产物**。
→ 对策：`make clean` 后重编，或 rsync 时 `--exclude`（见 §0）。
→ 同类教训：**任何 benchmark 脚本第一步都必须重新编译**，并把编译命令与结果打印出来
（曾因忘记重编，白等一整轮旧二进制的输出）。
