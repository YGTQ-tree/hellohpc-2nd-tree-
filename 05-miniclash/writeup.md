# 05-miniclash：批量 MD5 碰撞生成

## 1. 题目要做什么

每行任务给出一个输入文件和两个输出文件。程序要生成两个不同文件，二者都以输入文件完整内容开头，并且 MD5 相同。输入最多 4 KiB；每个碰撞由已有的 `md5fastcoll` 实现搜索。

四个正式算例分别有 32、64、128、256 个任务。评测只运行一次，没有预热；目标机器给 32 个 CPU 核。因此总时间主要受独立碰撞任务的运行和排队影响。

## 2. 先定位可并行的工作

原 `run.sh` 按任务逐行调用 `md5fastcoll`，每个进程结束后才开始下一个。各任务有不同输入与输出路径，彼此没有数据依赖，所以可以同时启动多个碰撞搜索，再把并发数限制在本进程可用的 CPU 数以内。

实现上，脚本用 `nproc` 读取当前 CPU 亲和性可用的核数，并用 Bash 后台任务和 `wait -n` 控制同时运行的子进程数。评测通过 `taskset` 把程序绑在 32 个核上时，子进程继承同一亲和性，不会把工作扩展到未分配的核。所有子进程完成后，脚本才返回；计时覆盖整批任务。

## 3. 为并行搜索区分随机状态

`md5fastcoll` 默认把随机状态的一部分设为当前秒数，另一部分为固定常数。如果同时启动多个进程，它们可能在同一秒得到相同初始随机状态。我在 `run.sh` 中根据启动秒数、任务序号和进程号构造两个 32 位非零种子，通过程序已有的 `--seed1`、`--seed2` 参数传入。

这只是为独立搜索提供不同随机轨迹，不读取测试答案，不按样例类型分支，也不改变碰撞校验条件。种子只影响随机搜索从哪里开始；每个任务仍独立生成并写出完整碰撞结果。

## 4. 编译优化

将 Makefile 的编译选项从 `-O2 -march=native` 调整为 `-O3 -march=native -funroll-loops`。算法主体较多使用固定宽度整数、循环和位运算；更高级别优化与循环展开值得测试。编译在 legion 上成功。后续若目标编译器或评测容器不支持这些选项，应以目标环境编译结果为准。

## 5. 复现与正确性检查

测试都在私人服务器 `legion` 上进行，没有在本机执行碰撞计算。远程目录是本次新建的独立目录，避免覆盖其他比赛数据。进入 `05-miniclash/source_code` 后，使用仓库自带生成器产生输入，再运行 `./run` 和官方校验器：

```bash
make all -j8
python3 ../utils/gencase.py 32 cases/legion32 1001
./run cases/legion32/tasks.txt
python3 ../utils/verify.py cases/legion32/tasks.txt
```

大规模检查将任务数改为 256，并使用种子 4004。校验器逐项检查两文件内容不同、都保留完整输入前缀、MD5 相等；没有修改 `utils/` 下的生成、验证或评分脚本。

本次结果：

| 测试 | legion 24 核时间 | 校验 |
|---|---:|---|
| 32 个任务，生成器种子 1001 | 16.80 秒 | 32/32 通过 |
| 256 个任务，生成器种子 4004 | 46.47 秒 | 256/256 通过 |

## 6. 如何理解性能结果

legion 有 24 个核，比赛目标机有 32 核，所以这里验证的是并行流程和输出正确性，不能直接预测正式耗时。碰撞搜索带有随机性，题面也说明没有 warmup；每个规模只测一次，因此这两组时间包含明显的随机波动。正式成绩以 OJ 使用的 ARM 集群和正式输入为准。

复核时应重点确认：`nproc` 在分配下正确反映 CPU 亲和性；每组任务均完成；官方校验全部通过；不同任务的输出路径互不重复。若以后修改并发控制或种子构造，应重新生成不同种子的任务并运行完整校验。
